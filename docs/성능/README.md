# 칸토 성능 관리

성능 **검사(측정·문제 발견)** 와 **개선(수정·전후 비교)** 문서를 모아두는 폴더입니다.
기준값·측정 방법론의 상세는 → [`../설계/20260630-성능감사-프레임워크.md`](../설계/20260630-성능감사-프레임워크.md)

## 폴더 구조

```
성능/
├── README.md      ← (이 문서) 전체 통합 대시보드
├── 성능검사/       ← 각자 측정한 검사 문서 (_템플릿.md 복사해서 작성)
└── 성능개선/       ← 개선 작업별 전/후 지표 문서 (_템플릿.md 복사해서 작성)
```

## 작업 흐름

1. **검사**: `성능검사/_템플릿.md`를 복사해 `이름-성능검사.md`로 만들고, 맡은 페이지를 측정해 채운다.
2. **통합**: 작성 후 아래 **통합 진행 현황** 표에 본인 페이지 결과를 한 줄씩 추가한다.
3. **개선**: 검사에서 나온 P0/P1 문제는 `성능개선/_템플릿.md`를 복사해 개선 작업 문서를 만들고, 전/후 지표를 기록한다.

> 측정 공통 규칙: **PSI · 배포 URL · 모바일+데스크탑 둘 다 · 2회 이상 대표값 · Lab 기준**

## 통합 개선 우선순위

검사에서 나온 개선 필요사항 중 P0/P1을 모아 추적한다. 개선 작업 시작 시 문서 링크를 건다.

> **전수 확인 결과 (2026-07-06, 6개 개선 문서 기준): 코드 반영은 6/6 완료. 15개 측정 페이지 전체 재측정 완료(2026-07-06 기준 안 한 페이지 없음).** **데스크탑은 측정된 모든 페이지에서 🟢 유지·개선** — 예외 없음. 모바일은 페이지별로 갈린다: main만 뚜렷이 개선. **usedgoods(2.6s→8.3s), rental-detail(2.8s→4.83s), go(TBT 480→1999ms), terms/service·youth·payment(5s대→7s대)는 실패로 판정할 만큼 명확히 악화**됐고, terms/policy·privacy·job-detail·signup은 모바일 편차가 크거나 결과가 뒤섞여 있다. 전역-sentry지연로딩은 페이지별 재측정으로는 직접 검증되지 않았지만, 거의 모든 페이지에서 공통으로 "미사용 JS 증가" 신호가 나온 것과 관련 있어 보인다. usedgoods·main·terms(policy)는 일부 실제 PSI로도 확인했고, 나머지는 로컬 Lighthouse 도구 기준 참고치라 실제 PSI 재확인이 남아있다.

## 2차 개선안 — 회귀 원인 조사

위에서 ❌ 실패로 판정된 회귀들의 원인을 코드 레벨로 추적했다. 상세는 → [2차개선안.md](./성능개선/2차개선안.md)

- **`usedgoods`/`rental-detail` 회귀 원인 확정**: 커밋 `3b38b46`(PR #582, "이미지 렌더링 느린 에러 해결")이 `ContentCard`/`ImageCarresel`의 캐러셀 인접 이미지를 항상 `loading="eager"`로 되돌려, 공통-LCP 개선의 "보이는 이미지만 priority" 원칙이 깨짐.
- **`/go` 회귀 원인 확정**: 지연 로딩 래퍼 `GoMapClient.tsx`가 어디에서도 import되지 않는 죽은 코드였음 — 실제 배포된 `page.tsx`는 `GoClient.tsx`를 직접 렌더링하고, 그 안에서 Google Maps SDK를 정적으로 import하고 있어 "완료" 표기와 달리 지연 로딩이 전혀 적용되지 않은 상태.
- **`terms/service·youth·payment` 회귀는 원인 미확정** — SSR/ISR 전환 자체는 코드상 정상 배포된 것으로 확인됨. Notion API 캐시 타이밍 또는 전역 번들 증가와의 연관성 등 추가 조사가 필요.

2차 개선 작업을 실제로 진행할 때는 이 저장소 관례대로 `성능개선/` 폴더에 새 전/후 비교 문서를 만든다.
