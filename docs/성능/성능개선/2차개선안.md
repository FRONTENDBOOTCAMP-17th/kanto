# 2차 개선안 — 배포 후 재측정에서 발견된 모바일 회귀 원인 조사

- **담당자**: 미정 (팀 논의 필요)
- **대상 페이지**: `/usedgoods`, `/rental/[id]`, `/go`, `/terms/service`, `/terms/youth`, `/terms/payment` (그 외 `/terms/policy`, `/terms/privacy`, `/signup`도 관련 의심)
- **관련 문서**: [../README.md](../README.md) "배포 후 재측정 비교" · [공통-LCP이미지우선순위및캐시TTL.md](./공통-LCP이미지우선순위및캐시TTL.md) · [go-맵동적로딩.md](./go-맵동적로딩.md) · [terms-SSR전환.md](./terms-SSR전환.md)
- **우선순위**: P0
- **상태**: 조사 중 — 원인 2건 확정(§2), 나머지 조사 필요(§3)

## 1. 배경

2026-07-06, 1차 배포된 6개 성능개선 작업을 검증하기 위해 15개 측정 페이지를 전부 재측정했다. **데스크탑은 예외 없이 전부 🟢 유지·개선**됐지만, **모바일은 다수 페이지에서 개선 전보다 오히려 나빠지는 회귀**가 발견됐다. 이 문서는 그 회귀들의 원인을 코드 레벨에서 추적한 결과와, 확인된 원인에 대한 2차 개선안을 정리한다.

## 2. 확정된 원인 (코드로 직접 검증됨)

### 2-1. `usedgoods` / `rental-detail` — 캐러셀 인접 이미지 "항상 eager 로딩"으로 되돌아감

- **원인 커밋**: `3b38b46` "bug: 이미지 렌더링 느린 에러 해결" (PR #582, 2026-07-06 13:53, dongkeun) — 우리가 재측정을 시작하기 전에 이미 배포돼 있었다.
- **무엇이 바뀌었나**: `src/components/common/ContentCard.tsx`와 `src/app/(user)/rental/[id]/_components/ImageCarresel.tsx`에서, 캐러셀의 이전/다음(인접) 이미지를 `invisible` 클래스로 화면에는 안 보이게 하면서도 `loading="eager"`를 줘서 **항상 네트워크로 미리 받아오도록** 바꿨다.
- **왜 회귀인가**: [공통-LCP이미지우선순위및캐시TTL.md](./공통-LCP이미지우선순위및캐시TTL.md)의 핵심 설계는 "실제로 화면에 보이는 첫 이미지에만 `priority`를 주고 나머지는 lazy 유지"였다(이유는 그 문서 §1-1 참고 — 모든 이미지에 priority를 주면 의미가 없어지고 초기 로드 용량이 늘어남). 이번 커밋은 "이미지 렌더링 느린 에러"라는 다른 문제를 고치려다 이 원칙을 깨고, 보이지도 않는 인접 이미지까지 즉시 로드하게 만들었다. Slow 4G로 시뮬레이션되는 모바일 측정에서는 여러 이미지가 동시에 대역폭을 다투게 되고, 그 결과 진짜 LCP 대상 이미지의 도착이 늦어진다.
- **영향 범위**: `ContentCard`를 쓰는 `usedgoods`/`rental`/`main` 목록 전체, `ImageCarresel`을 쓰는 `rental/[id]` 상세. (`usedgoods/[id]` 상세는 별도 컴포넌트를 쓰는지 확인 필요 — §3-4 참고)

### 2-2. `/go` — 지도 지연 로딩 개선이 실제로는 적용되지 않고 있음 (죽은 코드)

- **확인 방법**: `grep -rn "GoMapClient" src/` 결과, `GoMapClient.tsx` 자기 자신의 `export default function GoMapClient()` 정의 한 줄만 나온다. **다른 어떤 파일도 이 컴포넌트를 import하지 않는다.**
- **실제 렌더링 경로**: `src/app/(user)/go/page.tsx` → `GoClient.tsx`를 직접 렌더링. `GoClient.tsx` 최상단에서 `import { Map, useMap, ... } from "@vis.gl/react-google-maps";`로 **Maps SDK를 정적으로 import** — [go-맵동적로딩.md](./go-맵동적로딩.md)가 만든 `next/dynamic(ssr:false)` 지연 로딩 래퍼(`GoMapClient.tsx`)를 전혀 거치지 않는다.
- **추정 경위**: `GoMapClient.tsx`는 커밋 `fbbd3c2`("칸토고 성능개선 및 문서 작성")에서 만들어졌지만, 그 이후에도 `GoClient.tsx`에 여러 기능 커밋(모달, 애니메이션, 번개모임 실시간 동기화 등)이 계속 쌓였다. 병합 과정에서 `page.tsx`가 `GoMapClient`를 참조하도록 바뀌지 않았거나, 나중에 다시 `GoClient.tsx` 직접 렌더링으로 돌아간 것으로 보인다.
- **결과**: `go-맵동적로딩.md`의 "상태: 완료"는 사실과 다르다 — 코드는 작성됐지만 배포된 페이지는 그 코드를 쓰지 않는다. TBT가 480ms→1999ms로 4배 가까이 나빠진 것과 정확히 들어맞는다.

## 3. 원인 조사 필요 (미확정)

### 3-1. `terms/service`·`terms/youth`·`terms/payment` — 모바일 LCP가 세 페이지 모두 5s대 → 7.1~7.3s대로 나란히 악화

- **배제한 가설**: SSR+ISR 전환 자체의 문제는 아닌 것으로 보인다. 코드 확인 결과 `src/app/(user)/terms/[type]/page.tsx`는 `export const revalidate = 86400`과 서버 사이드 `getNotionPage()` 호출이 정상적으로 들어가 있고, `TermsContent.tsx`도 `"use client"`가 없어 `react-markdown` 렌더링이 서버에서 실행된다(예전 검사 문서가 지적했던 "클라이언트에서 마크다운 파싱" 문제는 이미 해결된 상태).
- **남은 가설**:
  - (a) Notion API 응답 캐시 — `src/services/notion/notion.ts`의 `getNotionPage`는 인메모리 `Map` 캐시(TTL 1시간)를 쓰는데, Vercel 서버리스 환경에서는 함수 인스턴스가 자주 새로 뜨기 때문에 이 캐시가 기대만큼 재사용되지 않을 수 있다. ISR(`revalidate=86400`)이 페이지 HTML 자체를 캐싱하지만, 재검증 시점에 걸리면 그 요청은 Notion API를 다시 타게 되고 그게 마침 측정 시점과 겹쳤을 가능성.
  - (b) 다른 페이지들에서도 공통으로 관찰된 "미사용 JS 증가" 전역 요인(§3-2)과 연결돼 있을 가능성.
- **확인 방법**: Vercel 함수 로그/트레이스에서 해당 요청들의 TTFB와 Notion API 호출 여부 확인, 측정 시각이 ISR 재검증 타이밍과 겹쳤는지 대조.

### 3-2. 전역 "미사용 JS(unused JS)" 증가

- 이번에 재측정한 거의 모든 페이지에서 미사용 JS가 원래 202~410KiB 수준이던 것이 300~600KiB대로 늘어난 것으로 나타났다(모바일·데스크탑 공통, 회귀 여부와 무관하게 전 페이지에서 관찰됨).
- Sentry Replay 지연 로딩([전역-sentry지연로딩.md](./전역-sentry지연로딩.md))은 코드 확인 결과 정상 배포돼 있다(`instrumentation-client.ts`에 `lazyLoadReplay` 지연 로직 존재, 레거시 `sentry.client.config.ts`도 삭제된 상태) — 즉 이 부분은 원인이 아니다.
- **확인 방법**: `npm run analyze`(번들 분석)를 2026-07-02 시점 커밋과 현재 커밋 각각에서 실행해 실제 번들 크기를 비교하고, 그 사이 병합된 PR 중 전역 엔트리(루트 레이아웃, 프로바이더, 의존성 추가)에 영향을 준 것이 있는지 재검토.

### 3-3. `/signup` 회귀 vs `/login` 개선의 불일치

- 같은 회원 관련 플로우인데 `/login`은 데스크탑에서 서비스 내 최고 수준으로 개선(LCP 4.3s🔴→1.07s🟢)된 반면 `/signup`은 모바일·데스크탑 모두 전 지표가 나빠졌다.
- 원인 미상 — 두 페이지의 최근 커밋 이력·번들 구성 차이를 비교해봐야 한다.

### 3-4. `usedgoods/[id]` 상세는 왜 영향이 없었나 (참고, 조사 우선순위 낮음)

- `usedgoods/[id]`는 이번 재측정에서 큰 변화가 없었다(3.1s🟡→3.75s🟡). §2-1의 `ImageCarresel.tsx`는 `rental/[id]`가 쓰는 컴포넌트이므로, `usedgoods/[id]`가 같은 문제의 영향을 받지 않는다면 서로 다른 캐러셀 구현을 쓰고 있다는 뜻이다 — 컴포넌트 공유 현황을 한 번 정리해두면 향후 유지보수에 도움이 될 것.

## 4. 2차 개선안 (우선순위 제안)

| 순위 | 작업 | 대상 | 근거 |
|:---:|------|------|------|
| P0 | `ContentCard`/`ImageCarresel`의 인접 이미지 "항상 eager" 로딩을 되돌리기 — hover/touch 등 실제 상호작용 시점에만 프리로드하거나, 최소한 `loading="lazy"`로 복귀 | usedgoods, rental, main 목록 / rental 상세 | §2-1 확정 원인 |
| P0 | `/go/page.tsx` → `GoClient.tsx`가 아니라 실제로 `GoMapClient.tsx`(지연 로딩 래퍼)를 쓰도록 연결 — 또는 `GoClient.tsx` 내부의 Maps SDK 정적 import를 `next/dynamic`으로 교체 | go | §2-2 확정 원인 |
| P1 | terms 3페이지 공통 악화 원인 확인(Notion API 타이밍 vs 전역 번들) 후 대응 | terms/service·youth·payment (+privacy·policy 재확인) | §3-1, 원인 미확정 |
| P2 | 번들 분석으로 전역 미사용 JS 증가분 원인 특정 | 전 페이지 | §3-2, 원인 미확정 |
| P2 | signup 회귀 원인 조사 | signup | §3-3, 원인 미확정 |
