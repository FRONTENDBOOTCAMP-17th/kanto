# 중복 로그인 방지 — 다른 기기 로그인 시 즉시 로그아웃 + 토스트 알림

작성: `DoHyuk-Centric`
일자: 2026-07-04

## 1. 배경 (발단)

로컬 개발 중 dev 서버 로그에 `Invalid Refresh Token: Refresh Token Not Found`(400,
`refresh_token_not_found`)가 요청마다 반복해서 찍히는 현상이 있었다. 원인은 코드가
아니라 **브라우저에 남은 오래된 Supabase 세션 쿠키**였다. 노트북 브라우저에 예전
세션의 `sb-` 쿠키가 남아 있는데 그 refresh token이 서버에서 이미 사라진 상태라,
`src/proxy.ts`의 `supabase.auth.getUser()`가 매 요청 갱신을 시도하다 실패한 것.
(해결: 쿠키 삭제 후 재로그인)

이를 계기로 "한 계정이 여러 기기에서 동시에 로그인되는 상황"을 어떻게 다룰지
논의했고, 다음 정책을 채택했다.

- **한 계정당 활성 세션 1개** (새 로그인이 이기고, 기존 기기는 로그아웃)
- 쫓겨나는 기기에는 **"다른 기기에서 로그인되어 로그아웃되었습니다" 토스트**로 안내
- 쫓겨나는 시점은 **즉시** (새 로그인 발생과 거의 동시에)

## 2. 전제 조건 — Supabase 대시보드 옵션

Supabase 대시보드 → Authentication → Sessions →
**"Enforce single session per user"** 를 켠다 (Pro 플랜 기능).

단, 이 옵션만으로는 "즉시"가 안 된다. 서버는 기존 세션의 **refresh token만**
무효화하기 때문에, 기존 기기가 들고 있는 access token(JWT)은 만료 전까지(기본
1시간) 그대로 유효하다. 기존 기기는 **다음 토큰 갱신 시점**에야
`refresh_token_not_found`를 받고 로그아웃된다. 서버가 클라이언트에 먼저 알려주는
통로가 없으므로, 즉시성을 위해서는 별도의 실시간 알림이 필요하다.

## 3. 설계

두 장치를 병행한다. 역할 분담:

| | Realtime broadcast (이번 구현) | 대시보드 single session 옵션 |
|---|---|---|
| 역할 | **즉시성 (UX)** — 새 로그인 순간 기존 기기 로그아웃 | **확실성 (보안)** — 서버에서 세션 자체를 무효화 |
| 한계 | 탭이 닫혀 있거나 절전이면 broadcast를 못 받음 | 토큰 갱신 시점(최대 JWT 만료 시간)까지 지연 |

broadcast를 못 받은 기기도 결국 옵션이 토큰 갱신 시점에 잡아주므로, 두 장치를
함께 쓰는 것이 전제다.

### 3-1. 세션 식별 — JWT `session_id` 클레임

"기기(로그인) 단위" 식별자로 access token 안의 `session_id` 클레임을 쓴다.

- 로그인할 때마다 새로 발급되고, **토큰이 갱신돼도 유지**된다.
- 같은 브라우저의 탭들은 세션을 공유하므로 같은 `session_id`를 가진다
  → 자기 자신(및 같은 브라우저의 다른 탭)을 쫓아내지 않는 판별 기준이 된다.

### 3-2. announce — 로그인 지점이 아니라 useAuthInit에서

로그인 경로가 둘이다: 이메일(`/api/login` → `setSession`)과 OAuth(`/auth/callback`
리다이렉트). 각 지점에 broadcast 코드를 넣는 대신, `useAuthInit`의
`onAuthStateChange`에서 **"처음 보는 세션 ID면 announce"** 방식으로 한 곳에
구현했다.

- localStorage(`kanto-announced-session`)에 마지막으로 announce한 세션 ID를 기록
- 인증 이벤트에서 받은 세션 ID가 기록과 **다를 때만** broadcast
- 효과: 두 로그인 경로 모두 자동 커버, 토큰 갱신·탭 전환·새로고침에서는 같은
  ID라 broadcast 없음, 같은 브라우저 다른 탭도 localStorage 공유로 중복 없음

주의: supabase-js v2의 `SIGNED_IN` 이벤트는 탭 refocus 등에서도 재발생할 수
있으므로, "이벤트 종류"가 아니라 "세션 ID가 바뀌었는가"로 판별하는 것이 핵심이다.

### 3-3. kick — 구독 중 다른 세션 ID를 받으면 로컬 로그아웃

로그인 상태인 동안 `session-sync:{authId}` 채널을 구독하고, **내 세션 ID와 다른**
`new-login` 이벤트가 오면 `supabase.auth.signOut({ scope: "local" })`을 호출한다.

- `scope: "local"`이 중요 — 기본값(global)이면 방금 로그인한 새 기기의 세션까지
  죽여버린다.
- 로컬 로그아웃은 `SIGNED_OUT` 이벤트를 발생시키므로, 아래 3-4의 토스트 로직이
  그대로 이어받는다.

### 3-4. 토스트 — "직접 로그아웃"과 "쫓겨난 로그아웃" 구분

`SIGNED_OUT` 이벤트만으로는 둘을 구분할 수 없다. 의도적 로그아웃(헤더 로그아웃
버튼, 회원탈퇴)은 `signOut()` 호출 **직전에** localStorage에 플래그
(`kanto-manual-signout`)를 남기고, `SIGNED_OUT` 핸들러에서:

- 플래그 있음 → 지우고 조용히 종료 (직접 로그아웃)
- 플래그 없음 → 강제 로그아웃으로 판단, `kickedOut` 상태를 3초간 켬
  → Header가 공용 `Toast`로 "다른 기기에서 로그인되어 로그아웃되었습니다" 표시

메시지는 `Header.kickedOut` 키로 ko/en/fil 3개 언어에 추가했다.

## 4. 알려진 한계 (수용한 트레이드오프)

1. **public broadcast 채널** — userId를 아는 제3자가 가짜 `new-login` 이벤트를 쏴
   강제 로그아웃을 유발할 수 있다. 로그아웃만 될 뿐 세션 탈취는 불가능해 피해가
   제한적이라 수용. 제대로 막으려면 Realtime private channel(RLS) 설정 필요.
2. **같은 브라우저 다중 탭 + 직접 로그아웃** — 한 탭에서 로그아웃 시 다른 탭이
   플래그 제거 타이밍에 따라 토스트를 잘못 볼 수 있는 드문 경우가 있다. 단순
   구현 유지를 위해 수용.
3. **닫힌 탭/절전 기기** — broadcast를 못 받으므로 즉시 로그아웃되지 않는다.
   대시보드 옵션이 토큰 갱신 시점에 잡아주는 것으로 커버(2장 참고).
