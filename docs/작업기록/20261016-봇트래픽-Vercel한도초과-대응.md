# 봇 트래픽으로 인한 Vercel Hobby 한도 초과 대응 (2026-10-16) — 박소유

- **관련 이슈**: #718 (제목상 관련으로 보이는 이슈: #658, #660)
- **PR**: #724 (`fix/server-traffic`), 테스트 브랜치 `test/718-call-count`
- **상태**: 진행 — #724 리뷰 대기, ISR 캐싱 미착수

> 이 문서의 개선 효과는 **개발 환경 측정 + 가정에 기반한 추정**입니다. Active CPU와 Fast Origin Transfer는 배포 후 Vercel Usage로 확인해야 하며, 아직 측정하지 못했습니다.

---

## 1. 배경

Vercel Usage(10/13 기준)가 Hobby 한도를 넘었습니다.

| 지표 | Hobby 한도 | 10/13 기준 | 비고 |
| --- | --- | --- | --- |
| Active CPU | 4 CPU-hrs | 7h23m | 초과 (-46% 이상 필요) |
| Fast Origin Transfer | 10 GB | 13.78 GB | 초과 (-27% 이상 필요) |
| Function Invocations | 1,000,000 / 월 | 699K (70%) | 한도 내 |
| CDN Requests | 1,000,000 / 월 | 360K (36%) | 한도 내 |

- 한도 초과 시 Hobby는 30일이 지나야 해당 기능을 다시 쓸 수 있고, 이미 쌓인 사용량은 줄지 않습니다. 앞으로의 누적을 막는 것이 목적입니다.
- 로그 확인 결과 `/job/[id]`를 쉬지 않고 순회하는 요청이 있었고, UA(Chrome 99/116/123 등)와 국가가 계속 바뀌었습니다. 요청 1건마다 함수가 실행되고 Supabase 5회(notices 1, jobs 3, 조회수 RPC 1)와 Sentry 전송이 발생했습니다.
- 실행 시간·메모리: 이슈에는 "요청당 약 119ms, 메모리 약 300MB"로 기록했으나 출처가 평균 추정치입니다. 로그에서 직접 확인한 단일 요청은 함수 실행 255ms, 메모리 311MB였습니다.

## 2. 방향

방화벽으로 봇을 완벽히 구분하기 어려워서(브라우저로 위장, UA·국가 변경), **봇도 유저로 보고 요청당 비용을 줄이는 쪽**으로 잡았습니다.

## 4. 측정 결과

### 4-1. 단위 테스트 (페이지 단위, 비로그인)

`generateMetadata` + 페이지 본문 + `after()`를 한 번 실행하고 Supabase 호출을 셌습니다. `notices`는 레이아웃에서 나가므로 포함되지 않습니다.

| 항목 | 개선 전 | 개선 후 (#724) |
| --- | --- | --- |
| `jobs` 조회 | 3회 | 2회 |
| 조회수 RPC | 1회 | 1회 |
| 페이지 단위 합계 | 4회 | 3회 |
| Sentry `tracesSampleRate` | 1 | 0.1 |
| Sentry `enableLogs` | 켜짐 | 꺼짐 |

개선 전 코드(`c6e95de`)로 되돌려 같은 테스트를 돌렸을 때 5건이 실패하는 것을 확인했습니다. 즉 테스트가 문제를 실제로 잡아냅니다.

### 4-2. 실제 Next 서버 (`next dev`) + 가짜 Supabase 서버

단위 테스트의 `React.cache`는 React 렌더 컨텍스트가 없어 **흉내 낸 구현**이라, 실제 서버 렌더링에서도 중복이 제거되는지 따로 확인했습니다.

- 로컬에 가짜 Supabase 서버를 띄우고 `NEXT_PUBLIC_SUPABASE_URL`을 그쪽으로 지정해 `next dev`를 실행
- `/job/<암호화 ID>`를 비로그인으로 요청해 가짜 서버에 들어온 요청을 집계 (워밍업 요청 후 측정)

| 1요청당 Supabase 요청 | notices | jobs | 조회수 RPC | 합계 | HTTP |
| --- | --- | --- | --- | --- | --- |
| 개선 전 | 1 | 3 | 1 | **5** | 200 |
| 개선 후 (#724) | 1 | 2 | 1 | **4** | 200 |

- 개선 전의 `notices 1 + jobs 3 + RPC 1 = 5`는 Vercel 로그에서 관찰한 패턴과 일치합니다.
- 실제 서버 렌더링에서도 `React.cache`가 `generateMetadata`와 페이지의 조회를 합치는 것을 확인했습니다.
- 팀 Sentry로 테스트 이벤트가 나가지 않도록 운영 모드(`next start`)가 아닌 개발 모드로 측정했습니다 (Sentry는 `NODE_ENV=production`에서만 활성화).

### 4-3. 측정 한계

- `next dev` 기준이며 운영 빌드·Vercel 환경은 아닙니다.
- 가짜 Supabase 응답, 비로그인 1요청 기준입니다. 로그인 사용자의 좋아요·신고 조회는 포함하지 않았습니다.
- **Active CPU, Fast Origin Transfer는 측정하지 못했습니다.** 배포 후 Usage에서 Before(10/13)와 비교해야 합니다.
- 첫 측정에서 가짜 데이터가 부족해 HTTP 500이 났고, 그때는 `jobs` 조회가 더 많이 찍혔습니다 (개선 전 4회, 개선 후 3회). 원인은 확인하지 않았고, 데이터를 보강해 HTTP 200으로 다시 측정한 값만 위 표에 기록했습니다.

## 5. 결정·보류

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| `proxy.ts`에서 `/job/[id]` 제외 | 보류 | 쿠키 없는 요청의 proxy는 로그상 6~20ms·외부 호출 없음이라 절감이 작고, matcher에서 제외하면 로그인 사용자의 세션 갱신이 빠질 위험이 있어 ISR 작업 때 함께 판단 |
| Vercel Rate Limit 룰 | 보류 | CDN Requests가 36%로 여유 있음. 캐싱 적용 후 추이를 보고 결정 |
| UA 차단 룰 | 사용 안 함 | UA가 계속 바뀌고 위조가 쉬움 |
| Attack Mode | 비상용으로만 | Vercel 검증 봇 목록(Googlebot, Bingbot, 네이버, 카카오톡, Facebook/LinkedIn/Twitter 미리보기)은 통과하지만, Slack/Notion 미리보기는 확인한 목록에 없어 깨질 수 있음 |
