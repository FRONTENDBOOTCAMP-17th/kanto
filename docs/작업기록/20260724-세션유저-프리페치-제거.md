# 세션 유저 프리페치 제거 — Vercel 캐싱 비용(Fast Origin Transfer, Fluid Active CPU) 절감 1차 수정

- **날짜**: 2026-07-24

Vercel 비용 급증(Fast Origin Transfer, Fluid Active CPU 무료 한도 초과 → Pro 전환) 원인 분석 및 1차 수정.

---

## 배경 — 문제 발견

Vercel 대시보드에서 **Fast Origin Transfer**, **Fluid Active CPU** 두 항목이 Hobby 무료 한도를 초과해 Pro 플랜으로 전환됨.

### 원인 분석

루트 레이아웃(`src/app/layout.tsx`, 앱의 모든 페이지를 감싸는 최상위 레이아웃)에서 매 요청마다 실행되는 코드 중, 요청 시점에만 알 수 있는 정보(쿠키·헤더)를 읽는 지점이 **두 곳** 있었음. Next.js는 이런 지점이 하나라도 있으면 그 라우트 전체를 "빌드타임에 미리 만들어두는 정적 페이지"가 아니라 "요청이 올 때마다 서버에서 처음부터 다시 렌더링하는 페이지"로 취급함(Next.js 16.2.6 공식 문서, `node_modules/next/dist/docs` 기준: `cookies`/`headers`는 "Request-time API"이며 "layout이나 page에서 쓰면 그 route를 dynamic rendering으로 전환시킨다"고 명시).

1. **세션 유저 프리페치**: `getSessionUser()`(로그인한 유저 정보 조회) → 내부적으로 `cookies()`(`next/headers`) 사용.
2. **i18n 로케일 감지**: `next-intl`의 `getMessages()` → `src/i18n/request.ts`가 `NEXT_LOCALE` 쿠키와 `accept-language` 헤더를 읽으려고 `cookies()`, `headers()`를 직접 호출.

루트 레이아웃이 앱 전체를 감싸기 때문에, 이 두 곳 중 **어느 한쪽만 있어도** 사이트의 거의 모든 페이지(45개 중 명시적으로 dynamic 선언한 5개 포함, 나머지 40개까지)가 캐싱 없이 매번 서버에서 풀 렌더링됨. 결과적으로 방문자·검색엔진 크롤러가 페이지를 열 때마다 Vercel Function이 실행(→ Fluid Active CPU 과금)되고, 캐싱되지 않은 응답이 매번 오리진에서 전송(→ Fast Origin Transfer 과금)됨.

이번 작업은 **1) 세션 유저 프리페치만** 제거했고, **2) i18n 로케일 감지는 아직 미처리** 상태.

---

## 무엇을 수정했나

루트 레이아웃에서 서버 사이드 세션 유저 프리페치(`getSessionUser()`)를 제거. 이미 클라이언트에 동일한 역할을 하는 로직(`useAuthInit`, Supabase 브라우저 클라이언트 기반)이 별도로 존재했으므로, 서버 쪽은 "이동"이 아니라 **중복 제거**.

| 파일                                                | 변경 내용                                                                                                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `src/app/layout.tsx`                                | `getSessionUser()` import·호출 제거. `Promise.all`에서 `initialUser` 제거. `GlobalLayout`에 `initialUser` prop 전달 중단.                                                      |
| `src/components/common/GlobalLayout.tsx`            | `initialUser` prop 및 관련 `useAuthStore.setState(...)` 초기화 블록 제거. `Header`/`FloatingChatWidget`에 넘기던 `initialUser` 제거. 미사용 `useAuthStore`/`User` import 정리. |
| `src/components/common/Header.tsx`                  | `initialUser` prop 제거. `useAuthStore((s) => s.user) ?? initialUser` → `useAuthStore((s) => s.user)`로 단순화. 미사용 `AppUser` import 정리.                                  |
| `src/components/common/chat/FloatingChatWidget.tsx` | `initialUser` prop 제거. `storeUser ?? initialUser` → `useAuthStore((s) => s.user)` 직접 사용. 미사용 `User` import 정리.                                                      |

`getSessionUser()` 자체는 삭제하지 않음 — `rental`/`usedgoods`/`job` 목록 페이지, `go` 서비스, admin 권한 액션 등에서 여전히 정상적으로 사용 중이며, 이 페이지들은 원래도 유저별 데이터가 필요해 dynamic이어야 하는 곳들이라 이번 수정 범위에서 제외.

---

## 왜 이렇게 수정했나

- 루트 레이아웃에 있는 `cookies()` 호출 하나가 앱 전체의 캐싱을 막고 있어, 가장 영향 범위가 크면서도 코드 변경량은 가장 작은 지점이었음.
- 클라이언트에 이미 `useAuthInit()`(Supabase JS의 `onAuthStateChange`, 구독 시작 시 `INITIAL_SESSION` 이벤트로 현재 세션을 즉시 재조회)이 있어, 서버 프리페치를 제거해도 로그인 상태 자체는 별도 구현 없이 그대로 채워짐.
- next.config.ts의 `cacheComponents` 같은 실험적 캐싱 모델 도입(i18n 로케일 감지까지 포함한 근본 해결책)은 앱 전역의 데이터 페칭 방식을 다시 훑어야 하는 큰 변경이라, 비용 급한 불부터 끄기 위해 **최소 변경 옵션**을 우선 적용.

## 긍정적 효과

- 루트 레이아웃 자체에서는 더 이상 `cookies()`를 호출하지 않음 → i18n 로케일 감지(남은 dynamic 유발 요소)만 마저 제거되면, 페이지 대부분이 정적/ISR 캐싱 대상이 될 수 있는 상태가 됨.
- 서버(`initialUser`)·클라이언트(`useAuthInit`) 이중으로 유저 정보를 가져오던 중복 로직이 단일 경로(클라이언트)로 정리됨 — 코드 단순화.
- 여러 컴포넌트에 퍼져 있던 `storeUser ?? initialUser` 폴백 패턴 제거로 인증 상태 소스가 하나로 통일됨.

## 부정적 효과 / 트레이드오프

- **로그인 상태 표시 깜빡임**: 이전에는 서버가 `initialUser`를 미리 채워 첫 페인트부터 로그인 UI가 보였음. 이제는 클라이언트 하이드레이션 후 `useAuthInit`이 세션을 채울 때까지 아주 짧게 "로그아웃 상태"로 보일 수 있음.
  - **참고**: 이 깜빡임은 CPU 과다 사용의 *원인*이 아니라, 그 원인(서버의 `getSessionUser()` 호출)을 없애는 수정의 *부작용*임. 인과관계: ① 서버가 `cookies()`를 쓰는 `getSessionUser()`를 호출 → 페이지 캐싱 불가 → CPU/전송량 과다(진짜 원인) → ② 그 호출을 제거(오늘 수정) → ③ 그 결과로 로그인 표시가 살짝 늦어짐(깜빡임, CPU와 무관한 UX 트레이드오프).
- **이번 수정만으로는 Vercel 비용이 즉시 크게 줄지 않을 수 있음**: `src/i18n/request.ts`의 `cookies()`/`headers()` 호출(i18n 로케일 감지)이 아직 남아 있어, 이것만으로도 앱 전체가 여전히 dynamic 상태로 유지됨. 이 부분까지 처리해야 실질적인 캐싱 효과가 발생함.
- `getSessionUser()`를 그대로 사용하는 페이지(rental/usedgoods/job 목록 등)는 이번 수정과 무관하게 계속 dynamic — 의도된 범위 밖이라 손대지 않음.

## 검증

- UI 동작(로그인 상태 표시, 헤더/플로팅 챗 위젯) 브라우저 실사용 테스트는 아직 미실시.

### i18n 로케일 감지를 두 번째 원인으로 판단한 기준

단순 추측이 아니라 아래 4가지를 순서대로 확인해서 좁힌 결론:

1. **영향 범위가 세션 유저 프리페치와 동급**: `src/i18n/request.ts`도 세션 유저 프리페치(`getSessionUser`)와 마찬가지로 루트 레이아웃(`getMessages()` 호출 경로)에서 실행되므로, 이 한 곳이 앱의 모든 라우트를 감쌈. 개별 페이지 하나만 오염시키는 게 아니라 전체 캐싱을 막을 수 있는 지점이라는 점에서 같은 급으로 의심할 근거가 있었음.
2. **공식 문서상 독립적으로 dynamic을 유발하는 API를 "두 개" 직접 호출**: `src/i18n/request.ts:17-18`이 `cookies()`뿐 아니라 `headers()`까지 직접 호출. Next.js 16.2.6 공식 문서(Request-time APIs 목록)에 `cookies()`, `headers()` 둘 다 각각 단독으로도 route를 dynamic으로 만드는 API로 명시되어 있어, 세션 유저 프리페치를 없애도 이 지점 하나만으로 여전히 전체가 dynamic일 수 있다고 예상했음.
3. **소거법 — 실제 빌드로 반증 시도**: 세션 유저 프리페치를 제거한 뒤 `/terms/[type]`이 `revalidate = 86400` 선언에도 여전히 `ƒ Dynamic`으로 남는지 확인. 만약 세션 유저 프리페치만이 문제였다면 이 페이지는 그 수정 직후 `○`/ISR로 바뀌었어야 함. 그런데도 여전히 `ƒ`로 남아있다는 건, 그 이외의 무언가가 이 페이지(혹은 이 페이지를 감싸는 공통 레이어)에서 계속 dynamic을 유발하고 있다는 뜻.
4. **다른 원인 후보를 코드로 배제**: `/terms/[type]/page.tsx` 자체 코드를 읽어 확인 — `getSessionUser`, `createClient` 등 인증/쿠키 관련 함수 호출이 전혀 없음. 이 페이지가 유일하게 요청 시점 정보를 쓰는 지점은 `getLocale()`(next-intl) 하나뿐이고, 이건 결국 `src/i18n/request.ts`로 연결됨. 즉 "이 페이지를 dynamic으로 만들 수 있는 다른 후보가 없다"는 걸 코드로 소거한 뒤 남은 유일한 설명이 i18n 로케일 감지였음.

→ 구조적 근거(1, 2)와 실측 근거(3, 4)가 서로 일치했기 때문에 "가능성이 크다"고 판단.

### 빌드 결과로 i18n 로케일 감지 잔존 확인

`npx next build` 실행 후 `Route (app)` 표에서 라우트별 렌더링 방식(○ Static / ƒ Dynamic)을 확인:

```
○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand
```

- 정적 에셋류(`/apple-icon.png`, `/icon0.svg`, `/manifest.webmanifest`, `/robots.txt`, `/sitemap.xml`, `/opengraph-image` 등)만 `○ Static`.
- **그 외 거의 모든 페이지가 여전히 `ƒ Dynamic`** — `/`, `/main`, `/login`, `/signup`처럼 로그인 여부와 무관하게 보여줄 수 있는 페이지들도 포함.
- **핵심 증거**: `/terms/[type]`은 코드에 이미 `export const revalidate = 86400;`(ISR 캐싱 의도)이 선언돼 있는데도 빌드 결과는 여전히 `ƒ Dynamic`. 세션 유저 프리페치를 제거했음에도 이 페이지가 dynamic으로 남는다는 건, `src/i18n/request.ts`의 `cookies()`/`headers()` 호출(i18n 로케일 감지)이 그 `revalidate` 선언을 무시하고 라우트를 강제로 dynamic 처리하고 있다는 직접적 증거.
- 결론: 세션 유저 프리페치 수정만으로는 실제 캐싱 효과가 아직 발생하지 않음. i18n 로케일 감지까지 고친 뒤 동일한 빌드를 다시 돌려서, 로그인·언어와 무관한 페이지들(`/`, `/main`, `/terms`, `/terms/[type]` 등)이 `○`/ISR로 바뀌는지 재확인 필요. `/profile`·`/myposts`·`/rental`·`/usedgoods`처럼 유저별 데이터가 필요한 페이지는 이 부분을 고쳐도 `ƒ`로 남는 게 정상(의도된 동작).
- **미확인 항목**: 같은 빌드 로그 맨 아래 `ƒ Proxy (Middleware)`라는 줄이 출력됨. 저장소에 `middleware.ts` 파일은 없는데도 나타난 항목이라 정체를 확인하지 못함(Sentry `withSentryConfig` 또는 next-intl 플러그인이 자동 주입했을 가능성 추정). 이번 작업 범위 밖으로 남겨둠 — 원인 조사에 영향 줄 가능성이 있으니 후속 확인 필요.

## 세션 체크는 이제 어디서 하나 (참고)

루트 레이아웃에서 `getSessionUser()`를 제거했다고 로그인 체크 자체가 없어진 게 아니라, 서버 렌더링 시점 → 브라우저 마운트 시점으로 위치만 옮겨감:

- [src/hooks/useAuthInit.ts:30-64](src/hooks/useAuthInit.ts#L30-L64) — Supabase **브라우저** 클라이언트(`@/lib/supabase`)의 `onAuthStateChange`를 구독. 구독 시작 시 기존 세션이 있으면 즉시 콜백이 호출되고(`INITIAL_SESSION`), `users` 테이블을 조회해 `useAuthStore`(zustand)에 채움.
- [src/components/common/Header.tsx:61](src/components/common/Header.tsx#L61) — `useAuthInit()`을 호출하는 지점. 헤더가 마운트될 때 이 흐름이 시작됨.
- 이 로직은 이번에 새로 만든 게 아니라 원래부터 있던 코드 — 서버 프리페치(`initialUser`)와 중복으로 유저 정보를 가져오고 있었고, 이번 수정은 그 중복 중 서버 쪽만 제거한 것.

## 후속 (미처리)

- **i18n 로케일 감지 처리**: `src/i18n/request.ts`의 `cookies()`+`headers()` 호출 — 이걸 해결해야 앱 전체 캐싱이 실제로 살아남. 코드 리뷰에서 지적받아 조사해본 결과, 언어 전환 기능(`LanguageSwitcher` → 쿠키 저장 → `router.refresh()` → 서버가 쿠키 읽어 재렌더링) 자체가 이 `cookies()` 호출에 의존하고 있어서 단순 삭제가 불가능함을 확인. 경로 기반 다국어 라우팅(`/ko`, `/en`, `/fil`) 또는 `cacheComponents` 마이그레이션 중 하나가 필요한 별도 규모의 작업으로 판단해 이번엔 보류. 그 대신 아래 [로그인상태-3분법-처리](20260724-로그인상태-3분법-처리.md)를 먼저 처리함.
- **`ƒ Proxy (Middleware)` 정체 확인**: 빌드 로그에 나타나는데 출처 미확인 (위 "미확인 항목" 참고).
- 배포 후 Vercel 대시보드에서 Fast Origin Transfer / Fluid Active CPU 실제 감소 여부 모니터링. **i18n 로케일 감지를 고치기 전까지는 이 지표들이 줄어들지 않을 것으로 예상됨.**
- (장기) `cacheComponents: true` + `<Suspense>` 마이그레이션 검토 — 이번엔 리스크 대비 채택 안 함, 근본 해결책으로 후순위 검토.
