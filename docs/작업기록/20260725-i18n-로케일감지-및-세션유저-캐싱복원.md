# i18n 로케일 감지 및 세션 유저 프리페치 제거 — 정적 캐싱 실제 복원

- **날짜**: 2026-07-25
- 관련 작업: [20260724-세션유저-프리페치-제거](20260724-세션유저-프리페치-제거.md), [20260724-로그인상태-3분법-처리](20260724-로그인상태-3분법-처리.md)의 후속 — 이전 작업이 세션 중 리버트되어 이번에 i18n 원인과 함께 다시 적용함.

---

## 배경

이전 작업기록에서 Vercel 비용 급증(Fast Origin Transfer, Fluid Active CPU) 원인을 두 가지로 특정했었다:

1. **세션 유저 프리페치**: 루트 레이아웃의 `getSessionUser()` → `cookies()` 사용
2. **i18n 로케일 감지**: `src/i18n/request.ts`의 `cookies()`/`headers()` 사용

1번은 한 번 고쳤었으나 세션 중 코드가 리버트되어 원상 복구됐고, 2번은 언어 전환 기능이 그 쿠키 읽기에 의존하고 있어 단순 삭제가 불가능해 보류 중이었다. 이번에 실제 Vercel 로그를 확인하는 과정에서 `meta-externalagent`(메타 AI 크롤러) 같은 봇 트래픽이 캐싱 부재 때문에 전부 유료 Function 실행으로 처리되고 있는 걸 확인했고, 이를 계기로 2번(i18n)까지 처리하고 1번(세션 유저)도 재적용했다.

**중간 확인된 사실**: `next build` 결과 세션 유저 수정만으로는(1번 재적용 없이 2번만 적용) 효과가 전혀 없었다 — `layout.tsx`에 `getSessionUser()`가 남아있는 한 1번이 그대로 전체를 dynamic으로 묶어두기 때문. 두 원인 모두 제거해야 실제 캐싱이 살아난다는 이전 진단이 재확인됨.

## 무엇을 수정했나

### 1. i18n 로케일 감지 — 서버는 항상 기본 로케일, 전환은 클라이언트에서

언어 전환(`LanguageSwitcher` → 쿠키 저장 → `router.refresh()` → 서버가 쿠키 읽어 재렌더링) 흐름 자체가 `cookies()`/`headers()` 사용의 근거였기 때문에, 이 흐름을 클라이언트 전용으로 옮겼다.

| 파일 | 변경 내용 |
|---|---|
| `src/i18n/request.ts` | `cookies()`/`headers()` 읽기 전부 제거. 항상 `defaultLocale`("ko")과 그 메시지를 반환. next-intl 권장에 따라 `timeZone: "Asia/Manila"` 추가(빌드 중 `ENVIRONMENT_FALLBACK` 경고 해결, 프로젝트 내 기존 `MANILA_TZ` 상수와 동일 타임존). |
| `src/i18n/LocaleProvider.tsx` (신규) | 클라이언트 컴포넌트. 서버가 내려준 기본 메시지로 시작하고, 마운트 직후 `NEXT_LOCALE` 쿠키를 읽어 다르면 해당 로케일 메시지를 동적 `import()`로 불러와 교체. `useLocaleSwitcher()` 훅으로 `locale`/`setLocale`을 하위에 노출. 언어를 바꾸면 `document.documentElement.lang`도 같이 갱신. |
| `src/app/layout.tsx` | `<NextIntlClientProvider messages={messages}>` → `<LocaleProvider initialMessages={messages}>`로 교체. |
| `src/components/common/LanguageSwitcher.tsx` | `setLocaleCookie` + `router.refresh()`(서버 왕복) 대신 `useLocaleSwitcher().setLocale()`(클라이언트 즉시 전환) 사용. `useRouter`/`useTransition` 관련 코드 제거. |
| `src/app/(user)/terms/[type]/page.tsx` | **예외 처리**: 이 페이지는 next-intl 메시지가 아니라 Notion에서 언어별 실제 약관 콘텐츠를 서버에서 가져오는 페이지라, 전역 기본 로케일 고정의 영향을 받으면 비한국어 유저도 무조건 한국어 약관을 보게 되는 부작용이 생김. `next-intl`의 `getLocale()` 대신 이 페이지에서만 직접 `cookies()`로 `NEXT_LOCALE`을 읽도록 분리 — 이 페이지 하나만 의도적으로 dynamic 유지, 나머지 전체엔 영향 없음. |

### 2. 세션 유저 프리페치 재제거 + 로그인 상태 3분법 (재적용)

이전 작업기록([20260724](20260724-세션유저-프리페치-제거.md), [20260724 3분법](20260724-로그인상태-3분법-처리.md))과 동일한 내용을 다시 적용:

- `src/app/layout.tsx`: `getSessionUser()` 호출 제거, `GlobalLayout`에 `initialUser` 전달 중단
- `src/components/common/GlobalLayout.tsx`: `initialUser` prop 및 `useAuthStore.setState` 초기화 블록 제거
- `src/components/common/Header.tsx`: `initialUser` prop 제거, `authStatus`(3분법) 구독 추가해 초기화 중엔 로그인 버튼 대신 스켈레톤 표시
- `src/components/common/chat/FloatingChatWidget.tsx`: `initialUser` prop 제거
- `src/store/authStore.ts`: `status: "initializing" | "authenticated" | "unauthenticated"` 추가

## 검증 — 빌드로 실제 캐싱 전환 확인

`npx next build` 실행 후 라우트 테이블 비교:

**세션 유저만 있던 상태(이전 작업, i18n 미수정) 대비 이번 결과 — 새로 `○ Static`으로 전환된 라우트:**

```
○ /
○ /_not-found
○ /login
○ /notifications
○ /signup
○ /terms
```

**여전히 `ƒ Dynamic`인 라우트** (의도된 정상 상태 — 각 페이지 자신이 `getSessionUser()` 또는 `createClient()`를 직접 호출해 유저별/인증 데이터를 가져오기 때문):

- `/main` — `getActiveMeetups()`(`src/services/go/go.ts`)가 `createClient()` 사용
- `/rental`, `/usedgoods`, `/job` 등 목록/상세 페이지 — `getSessionUser()` 직접 사용
- `/admin/*`, `/profile`, `/myposts`, `/favorites`, `/create`, `/go` 등 — 유저별 데이터 필요
- `/terms/[type]` — 위에서 설명한 의도된 예외
- 모든 `/api/*` route handler — 원래도 요청 처리용이라 dynamic이 정상

**빌드 중 경고**: `ENVIRONMENT_FALLBACK`(next-intl, `timeZone` 미설정) 발견 → `timeZone: "Asia/Manila"` 추가로 해결, 재빌드 시 경고 없음 확인.

`npx tsc --noEmit -p tsconfig.json` — 오류 0건.

## 긍정적 효과

- 로그인 여부·언어와 무관한 페이지(`/`, `/login`, `/signup`, `/notifications`, `/terms` 등)가 실제로 `○ Static`으로 전환됨 — 이 페이지들은 이제 CDN에서 캐시로 응답 가능해져 Vercel Function 실행·Origin Transfer가 거의 발생하지 않음.
- 지난 작업기록에서 `/terms/[type]`이 `revalidate = 86400` 선언에도 여전히 dynamic이었던 문제가 실제로 해결됨(단, `[type]` 자체는 콘텐츠 언어 때문에 의도적으로 dynamic 유지, `/terms` 인덱스는 static 전환).
- 세션 유저·로그인 상태 3분법 재적용으로 지난 리뷰에서 지적된 "로그인 유저에게 로그인 버튼이 잘못 노출되는" 문제도 같이 해결된 상태로 복원됨.

## 부정적 효과 / 트레이드오프

- **언어 깜빡임(새로 발생)**: 한국어가 아닌 언어를 쓰던 유저는 페이지를 새로 열 때마다 아주 짧게 한국어 화면이 보였다가 클라이언트에서 자기 언어로 바뀜. 헤더 로그인 버튼 깜빡임보다 체감 범위가 큼(페이지 전체 텍스트). 사전에 팀에 고지한 트레이드오프.
- **로그인 상태 깜빡임(재발생)**: 세션 유저 프리페치 재제거로 인해, 3분법 처리에도 불구하고 초기화 중 짧은 스켈레톤이 다시 보임(이전 작업기록에서 이미 검토·수용한 트레이드오프).
- `/terms/[type]`은 여전히 개별적으로 dynamic — 이 페이지만은 캐싱 이득을 못 봄(의도된 선택).
- `/main`을 포함한 목록/상세 페이지들은 여전히 dynamic — 이 문서에서 다룬 두 원인 제거로는 캐싱되지 않음. 이 페이지들까지 캐싱하려면 각 페이지의 `getSessionUser()`/`createClient()` 사용 자체를 다시 설계해야 하는 별도 작업.

## 후속 (미처리)

- 배포 후 Vercel 대시보드에서 Fast Origin Transfer / Fluid Active CPU 실제 감소 여부 모니터링 (이번이 처음으로 두 원인을 모두 제거한 상태이므로, 실제 효과가 나타나야 정상).
- 브라우저 실사용 테스트: 언어 전환 시 깜빡임 체감, 로그인 상태 전환 체감 둘 다 미실시.
- `/main`, `/rental`, `/usedgoods`, `/job` 등 트래픽이 큰 목록형 페이지들은 여전히 dynamic — 필요 시 이 페이지들의 개인화 데이터 fetching 구조를 별도로 재검토(예: 공개 목록 부분과 유저별 부분을 분리해 부분적으로라도 캐싱).
- `ƒ Proxy (Middleware)`의 정체는 여전히 미확인 (이전 작업기록 참고).
