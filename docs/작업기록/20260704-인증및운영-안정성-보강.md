## 1. 배경

마감 전 인증, 공지, 약관, 관리자 감사 로그, 글 작성 제한처럼 사용자 흐름과 운영 안정성에 직접 영향을 주는 작은 취약 지점들이 발견됐다. 각각은 독립된 이슈지만 모두 "실패해도 서비스가 깨지지 않게 하고, 서버에서 반드시 보장해야 할 규칙은 서버로 옮긴다"는 방향으로 처리했다.

## 2. 로그인 요구·로그아웃 모달 디자인 정리

**문제:** 로그인 요구 모달과 로그아웃 확인 모달의 형태가 다른 화면들과 비교해 무겁고, 닫기/확인 액션 구성이 일관적이지 않았다.

**처리:**
- `ConfirmModal`을 더 작은 `w-80` 모달로 정리하고, 중앙 정렬 텍스트 + 단일 확인 버튼 구조로 단순화
- `LoginRequiredModal`도 같은 폭/모서리/그림자 톤으로 맞춤
- 로그인 이동 버튼의 색상과 press 인터랙션을 현재 디자인 톤에 맞게 조정

**변경 파일:**
- `src/components/common/ConfirmModal.tsx`
- `src/components/common/LoginRequiredModal.tsx`
- `messages/{ko,en,fil}.json`

## 3. 이메일 로그인 실패 횟수 응답 개선

**문제:** 이메일 로그인 실패 제한은 있었지만, 클라이언트가 현재 실패 횟수를 알 수 없어 사용자 안내를 세밀하게 하기 어려웠다.

**처리:**
- `/api/login` 실패 응답에 `failedAttempts`를 포함
- 5회 이상 실패 시에도 `failedAttempts: 5`를 내려 UI가 잠금 상태를 명확히 알 수 있게 함

**변경 파일:**
- `src/app/api/login/route.ts`
- `src/app/(user)/login/_components/LoginForm.tsx`
- `src/app/(user)/login/page.tsx`

## 4. 비밀번호 찾기 모달 검증 흐름 개선

**문제:**
- 이름/이메일/인증번호/새 비밀번호 입력의 검증 피드백이 늦거나 모호했다.
- 이름이 없는 경우와 이메일이 맞지 않는 경우가 같은 오류처럼 보였다.
- 인증 메일 발송이 응답을 지연시키고, 메일 설정이 없는 환경 처리가 명확하지 않았다.

**처리:**
- 단계별 상태를 `request → verify → reset`으로 유지하되, 필드별 `touched` 상태와 입력 ref를 추가
- 이름, 이메일, 인증번호, 새 비밀번호, 비밀번호 확인을 클라이언트에서 먼저 검증
- 서버에서 `name_not_found`, `email_not_found`를 분리해 응답
- 인증 메일 transporter를 캐싱해 반복 생성 비용을 줄임
- production에서 메일 설정이 없으면 명시적으로 실패 응답
- 메일 발송은 `after()`로 응답 이후 처리하고, 실패 시 저장된 인증 코드를 삭제
- 응답에 `Server-Timing`을 추가해 매칭/저장/총 소요 시간을 추적할 수 있게 함

**변경 파일:**
- `src/app/(user)/login/_components/FindPasswordModal.tsx`
- `src/app/api/auth/reset-password/route.ts`
- `src/utils/verificationCode.ts`

## 5. 약관 페이지 Notion null 방어

**문제:** Notion 페이지 조회가 `null`을 반환하면 구조 분해에서 런타임 에러가 발생할 수 있었다.

**처리:**
- `getNotionPage(pageId)` 결과를 먼저 `data`로 받고, 값이 없으면 안내 화면을 반환
- 이후에만 `title`, `content`를 구조 분해

**변경 파일:**
- `src/app/(user)/terms/[type]/page.tsx`

## 6. 공지 번역 API 실패 시 저장 보장

**문제:** 외부 번역 API가 실패하면 공지 저장 흐름까지 실패할 수 있었다.

**처리:**
- `translateText` 내부에서 외부 API 요청 실패, 비정상 응답, 빈 번역값을 모두 catch
- 실패 시 원문을 반환해 공지 저장 자체는 계속 진행

**변경 파일:**
- `src/lib/translate.ts`

## 7. 구인 글 작성 도배 방지 서버 강제

**문제:** 글 작성 제한을 클라이언트 API 호출에 의존하면 우회 가능성이 있었다.

**처리:**
- 구인 글의 `posts` 레코드 생성을 서버 액션 `createJobPostRecord`로 이동
- 세션 사용자 확인 후 `users.auth_id`로 내부 user id 조회
- 관리자 스팸 설정(`post_window_sec`, `post_max_count`) 기준으로 최근 작성 수를 서버에서 검사
- 제한 초과 시 `RATE_LIMIT` 오류를 던지고, 클라이언트는 기존 안내 메시지를 표시

**변경 파일:**
- `src/app/(user)/job/create/actions.ts`
- `src/hooks/useCreateJobForm.ts`

## 8. 감사 로그 기록 및 CI 보강

**문제:**
- 관리자 권한 부여/회수 액션에서 감사 로그 저장을 `await`하지 않아 실패를 놓칠 수 있었다.
- CI에서 타입 체크와 빌드는 수행하지만 lint가 별도로 드러나지 않았다.

**처리:**
- `promoteToAdmin`, `revokeAdmin`에서 `insertAuditLog`를 `await`
- GitHub Actions에 `npx eslint . --max-warnings=0` 단계 추가
- lint 단계는 `continue-on-error: true`로 둬 마감 시점의 경고 관측용으로 사용

**변경 파일:**
- `.github/workflows/ci.yml`
- `src/app/(admin)/admin/operation/permissions/actions.ts`
- 관리자 공지/신고/게시글/유저 관련 server action 및 API route의 유사 패턴 정리
