# 채팅 단일 책임 원칙 리팩토링 설계

## 1. 배경

채팅 도메인은 #694(`ChatRoom` + `ChatRoomClient` 병합), #696(폴더 재편 · 상태 zustand 이전 · 훅 분리)을 거치며 구조가 상당히 정리됐다. 그러나 정리 범위와 방식에 두 가지 공백이 남았다.

**첫째, 훅은 뽑았지만 컴포넌트는 쪼개지 않았다.** 로직을 커스텀 훅으로 추출해도 그 훅들을 호출하는 주체가 여전히 컴포넌트 하나뿐이면, 그 컴포넌트는 계속 여러 기능 영역을 직접 조율한다. `ChatRoom/_components/Content/index.tsx`가 훅 7개를 추출하고도 13개 책임을 지고 있는 것이 그 예다.

**둘째, 그룹 채팅은 범위 밖이었다.** `components/go/groupChat/`은 #694·#696에서 한 번도 손대지 않았고, 전수 조사 결과 1:1 채팅보다 상태가 나쁘다.

## 2. 목표

Chat 도메인에서 쓰이는 모든 컴포넌트 · 훅 · 서비스가 하나의 책임만 갖도록 한다. 파일 크기나 훅 개수는 우선순위를 정하는 참고 지표일 뿐 통과 기준이 아니며, "작아 보인다"는 이유로 검토를 건너뛰지 않는다.

## 3. 비목표

- 채팅 기능 및 UX 변경 — 순수 리팩터링으로 진행한다
- DB 스키마 변경 — `chats` 테이블의 `user_id_1_*` / `user_id_2_*` 쌍 컬럼 구조가 코드 전반에 삼항연산자를 유발하고 있으나, 마이그레이션이 필요한 별도 이슈로 분리한다
- AI 챗봇(`api/ai/chat/route.ts`, 252줄) — 이름만 chat이고 도메인이 다르다
- 상태 관리 라이브러리 추가 도입

### 4.1 선행 실험 기록 — 훅 합성은 반환값이 적을 때만

#696 작업 중 `useChatMessages` · `useChatRoomRealtime` · `useSpamPrevention` · `useSpamConfig` · `useSendMessage` 5개를 `useMessaging` 하나로 합성했다가 되돌린 이력이 있다. 다섯 훅이 같은 `setMessages`를 공유하고 있어 합성이 타당해 보였으나, 실제로 적용하니 호출부의 구조분해 반환값이 13개가 되면서 각 값이 어디서 온 것인지 보이지 않게 됐다.

**결론: 훅 합성은 책임이 서로 얽혀 있으면서 반환값이 적을 때만 적용한다.** 이 문서의 모든 제안은 "합치기"가 아니라 "쪼개기" 방향이며, 합성이 필요해 보이는 지점이 나오면 이 기준으로 판단한다.

## 8. 3순위 — ChatRoom Content

227줄, 책임 13개. 훅 7개가 이미 `_hooks/`로 추출되어 있으므로 "로직을 훅으로 뽑는" 작업은 끝났고, **여러 훅을 직접 호출하는 컴포넌트를 기능 영역별 컨테이너로 쪼개는** 작업만 남았다.

### 8.1 목표 구조

```
Content/
├── index.tsx                    공유 상태만 보유하고 섹션 조립
├── _components/
│   ├── MessagingSection.tsx     useChatMessages · useChatRoomRealtime
│   │                            useSpamConfig · useSpamPrevention · useSendMessage
│   │                            + MessageList + ChatInput
│   └── PaymentSection.tsx       useChatBannerState
│                                + ReviewBanner + 결제/계좌 미등록 모달

```

각 섹션 컴포넌트가 자기 영역에 필요한 훅을 직접 호출하고, `Content/index.tsx`는 여러 섹션이 공유하는 상태만 들고 조립하는 오케스트레이터로 축소한다.

### 8.2 미해결 쟁점 — `messages` 소유권

`messages`는 세 곳에서 필요하다.

- `MessageList` 렌더링 → MessagingSection
- `systemMsgCount` 계산 → `useChatBannerState` 인자 → PaymentSection
- `isCompleted` 계산 → `ChatHeader`의 `isReserved` / `onToggleReserve` 결정

섹션을 쪼개려면 `messages`를 어디에 둘지 결정해야 한다.

| 안 | 내용 | 평가 |
|---|---|---|
| (a) | `Content`가 계속 보유하고 섹션에 props로 전달 | prop drilling이 재발하므로 이번 리팩터링 목적과 충돌 |
| (b) | 방 단위 React Context 신설 | 방 수명과 상태 수명이 일치. **현재 선호안** |
| (c) | zustand 스토어로 승격 | 방을 나가면 사라져야 할 상태라 전역화는 과함 |

착수 시점에 (b)를 기준으로 검토하되, 구현 중 Context가 과하다고 판단되면 3순위 범위를 "섹션 분리 없이 유지"로 축소하는 것도 선택지에 둔다. **책임을 줄이려다 다른 문제를 만들면 하지 않는 편이 낫다** — 4.1의 `useMessaging` 사례와 같은 판단 기준을 적용한다.

## 9. 공통 선행 작업 — `useAutoDismissError` 승격

현재 위치는 `chat/room/ChatRoom/_components/Content/_hooks/useAutoDismissError.ts`이며 `Content/index.tsx`에서만 쓰인다. 1순위(그룹 채팅 토스트 2종)와 2순위(ChatHeader 토스트)가 모두 같은 로직을 필요로 하므로, 착수 전에 공용 위치로 옮긴다.

여러 도메인이 공유하는 훅을 특정 도메인 폴더 밑에 두면 다른 도메인이 그 폴더를 거꾸로 import하게 되어 도메인 분리가 깨진다(#696에서 `useSpamPrevention`을 `hooks/chat/`에 남긴 것과 같은 판단).

- 이동: `hooks/useAutoDismissError.ts`
- 확장 검토: `ChatHeader`의 토스트는 성공/실패 타입과 아이콘을 함께 받으므로, 승격 시 이 인자를 수용할지 아니면 별도 훅으로 둘지 판단 필요

## 10. 진행 순서와 검증

1. 9절 공통 작업 → 1순위 → 2순위 → 3순위 순으로 진행하고, 각 순위를 별도 PR로 분리한다.
2. 브랜치는 기존 컨벤션(`refactor/{이슈번호}-{설명}`)을 따른다.
3. 각 PR마다 다음을 확인한다.
   - `npx tsc --noEmit` 통과
   - `npx eslint src` — 신규 경고 0건(기존 경고 1건: `useChatRoomRealtime`의 exhaustive-deps)
   - 개발 서버 기동 후 실제 브라우저에서 동작 확인
4. 브라우저 확인 시나리오
   - 1순위: 그룹방 진입 시 안읽은 메시지 위치로 스크롤, 이전 메시지 로드 후 스크롤 위치 유지, 전송, 최신으로 점프, 멤버 차단(2가지 모드) 및 해제, 신고
   - 2순위: 메뉴 열기/바깥 클릭 닫기, 차단 및 해제, 중복 신고 차단, 예약 토글, 나가기
   - 3순위: 채팅방 진입 · 전송 · 뒤로가기 시 안읽음 뱃지 초기화, 새 채팅 초안 새로고침 복원, 결제 요청 흐름

리팩터링이므로 동작이 바뀌면 실패로 간주한다. 타입 체크와 린트는 정적 오류만 잡으므로 브라우저 확인을 생략하지 않는다.
