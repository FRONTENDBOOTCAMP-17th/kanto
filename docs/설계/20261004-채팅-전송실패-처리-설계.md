# 채팅 메시지 전송 실패 처리 설계

## 1. 배경

채팅 메시지 전송은 낙관적 UI(Optimistic UI)로 구현되어 있다. 전송 버튼을 누르면 임시 메시지(`tempId`)를 즉시 화면에 추가하고, 서버 응답이 오면 실제 `id`로 교체한다. 전송 후 화면 반영까지 100ms 이내임을 직접 측정으로 확인했다.

실패 처리에는 두 가지 공백이 있었다.

**첫째, 실패한 메시지가 말없이 사라졌다.** 요청이 실패하면 임시 메시지를 목록에서 제거하고 토스트만 띄웠다. 사용자는 어떤 메시지가 실패했는지 알 수 없고, 같은 내용을 다시 입력해야 했다.

**둘째, 응답이 없는 경우의 기준이 없었다.** 네트워크가 느려 응답이 오지 않을 때 언제까지 기다릴지, 언제 실패로 볼지 정해져 있지 않았다. 응답이 없다고 해서 저장되지 않은 것은 아니다. 서버는 저장을 끝냈지만 응답만 늦거나 유실될 수 있다.

## 2. 목표

- 전송에 실패한 메시지를 사용자에게 명확히 보여준다.
- 실패 시 재입력 없이 한 번의 동작으로 다시 보낼 수 있다.
- 느린 네트워크에서는 전송 중임을 알린다.
- 1:1 채팅과 그룹 채팅에 같은 방식으로 적용한다.

## 3. 비목표

- **DB 스키마 변경 없음.** 서버 변경은 읽기 전용 조회 액션 추가로 한정한다.
- **완전한 멱등성(`client_id` + 유니크 제약)은 이번 범위에서 제외한다.** 이유는 6.2에 정리했다.
- 실패한 메시지를 새로고침 이후에도 보존하지 않는다. 채팅방을 벗어나면 실패 상태는 사라진다.

## 4. 근거

| 기준 | 출처 | 적용 |
|---|---|---|
| 응답 시간 3단계 한계 0.1초 · 1초 · 10초 | Jakob Nielsen, 《Usability Engineering》 | 0.1초: 낙관적 UI로 즉시 반영 / 1초: "전송 중" 표시 / 10초: 실패 판단 |
| 응답 없음 ≠ 저장 안 됨 | 분산 시스템의 부분 실패 | 실패로 확정하기 전에 서버에 저장 여부를 확인한다 |
| 사용자가 접하는 UI는 적을수록 좋다 | 설계 원칙 | 재입력 요구 대신 버튼 한 번으로 재전송한다 |

## 5. 동작

### 5.1 상태

메시지에 `status` 필드를 둔다(`MessageWithSender`, `GroupMessageWithSender`).

| status | 의미 | 화면 |
|---|---|---|
| 없음 | 정상 또는 전송 후 1초 미만 | 일반 말풍선 |
| `sending` | 1초가 지나도 응답 없음, 또는 재전송 진행 중 | 반투명 말풍선 + 스피너와 "전송 중..." |
| `failed` | 실패 확정 | 반투명 말풍선 + "전송 실패" + 재전송·삭제 버튼 |

실패한 메시지는 대화 목록의 맨 아래에 고정해서 보여준다. 서버는 저장 순서로 메시지를 정렬하므로 재전송된 메시지는 어차피 맨 아래에 위치하며, 실패 메시지를 아래에 두면 재전송 전후 위치가 달라지지 않는다.

### 5.2 흐름

```
전송 버튼
  └ 임시 메시지 즉시 추가 (100ms 이내)
  └ 서버 요청 시작
        ├ 1초 경과, 응답 없음 → status = sending ("전송 중...")
        ├ 응답 도착 → 실제 id로 교체, status 제거
        ├ 요청 실패 → 서버에 저장됐는지 확인
        │     ├ 저장됨 → 성공으로 정정
        │     └ 없음 → status = failed (+ 오류 토스트)
        └ 10초 경과, 응답 없음 → 서버에 저장됐는지 확인
              ├ 저장됨 → 성공으로 정정
              └ 없음 → status = failed
실패 처리 이후 응답이 뒤늦게 도착하면 성공으로 정정한다.

재전송 버튼
  └ status = sending (버튼이 스피너로 바뀌어 연속 입력 차단)
  └ 보내기 전에 서버에 저장됐는지 먼저 확인
        ├ 저장됨 → 성공으로 정정
        └ 없음 → 같은 임시 메시지로 다시 전송 (위 흐름 반복)

삭제 버튼
  └ 임시 메시지 제거
```

### 5.3 서버 저장 확인 조건

메시지를 식별할 고유 번호가 없으므로 아래 조건을 **모두** 만족하는 행만 "저장됨"으로 인정한다.

- 같은 방(채팅), 내가 보낸 일반 메시지, 같은 내용
- 전송 시작 시각 30초 전 이후에 생성됨 (클라이언트와 서버의 시계 오차 여유)
- 화면에 이미 있는 같은 내용의 내 메시지 id가 **아님**

세 번째 조건이 없으면 과거에 보낸 같은 말("네")을 방금 보낸 메시지로 오인해, 실제로는 전송되지 않았는데 화면은 성공으로 표시한다.

### 5.4 Realtime으로는 확인할 수 없다

1:1과 그룹 채팅의 Realtime 핸들러는 `sender_id === currentUser.id`인 일반 메시지를 무시한다. 보낸 사람은 자기 메시지를 Realtime으로 받지 않으므로, 서버 액션의 응답 또는 별도의 읽기 조회만이 저장 여부를 알 수 있는 수단이다.

## 6. 대안 비교

### 6.1 실패 메시지를 어떻게 보여줄 것인가

| 방식 | 내용 | 판단 |
|---|---|---|
| A. 실패 메시지를 목록에 유지 + 재전송·삭제 | 말풍선에 상태와 버튼 표시 | **채택.** 어떤 메시지가 실패했는지 명확하고, 여러 건이 실패해도 각각 처리 가능 |
| B. 입력창으로 내용 복원 | 실패 시 메시지를 지우고 입력창에 되돌림 | 입력 중인 내용과 충돌하고, 어떤 메시지가 실패했는지 보이지 않음 |
| C. 자동 재시도 | 일정 횟수 재시도 후 실패 처리 | 서버에 이미 저장된 경우 중복 전송 위험 |

A의 목적은 시점 보존이 아니라 **실패를 명확히 알리는 것**이다. 서버가 저장 순서로 정렬하는 구조에서는 재전송이 원래 시점을 복원하지 못하므로(대화 맥락이 바뀐 뒤 보내는 "네 좋아요"는 다른 대화에 붙는다), 실패 메시지를 맨 아래에 고정하고 사용자가 재전송 여부를 직접 판단하게 한다.

### 6.2 중복 전송을 어떻게 막을 것인가

중복은 "서버는 저장에 성공했지만 응답이 10초를 넘겨 실패로 표시된 뒤 사용자가 재전송"할 때 생긴다.

| 방식 | 내용 | 판단 |
|---|---|---|
| `client_id` + 유니크 제약 | 요청마다 고유 ID를 보내고 DB 제약으로 중복 차단 | 보장됨. 두 메시지 테이블의 마이그레이션과 운영 DB 적용이 필요해 이번 범위에서 제외 |
| 내용·시간 휴리스틱 | 같은 내용이 최근 N초 안에 있으면 무시 | 같은 말을 일부러 연달아 보내는 경우 오작동 |
| **저장 여부 확인 후 재전송 (채택)** | 5.3의 조건으로 읽기 조회 후 판단 | 스키마 변경 없이 대부분의 중복을 차단 |

완전한 멱등성을 택하지 않은 이유는 다음과 같다.

- 스키마 변경과 운영 배포 부담이 이번 목표(실패 UX 개선)에 비해 크다.
- 중복이 생기는 조건이 좁다. 서버 저장 성공 후 응답이 10초를 넘겨야 한다. 발생 빈도는 측정하지 않았다.
- 중복이 생겨도 같은 메시지가 한 번 더 보이는 정도이며, 결제 등 금전 처리는 별도 흐름이다.
- 저장 확인과 재전송 버튼 비활성화로 대부분 완화된다.

## 7. 구현 위치

| 역할 | 파일 |
|---|---|
| 전송 추적(1초 · 10초 · 저장 확인 · 늦은 응답 정정) | `src/utils/chat/trackSend.ts` |
| 1:1 전송 훅 (전송 · 재전송 · 삭제) | `ChatRoom/_components/Content/_hooks/useSendMessage.ts` |
| 그룹 전송 훅 | `GroupChatRoom/_components/Content/_hooks/useGroupSendMessage.ts` |
| 1:1 저장 확인 서버 액션 | `common/chat/room/actions.ts` — `findSavedMessageAction` |
| 그룹 저장 확인 서버 액션 | `services/go/groupChat.ts` — `findSavedGroupMessage` |
| 상태 필드 | `type/chat/message.ts`, `type/groupChat.ts` |
| 말풍선 UI와 실패 메시지 하단 고정 | `MessageItem.tsx`, `MessageList.tsx`, `GroupMessageList.tsx` |
| 번역 키 | `messages/{ko,en,fil}.json` — `Chat.message*`, `Go.chat.message*` |

훅의 콜백은 최신 값을 ref로 읽어 참조를 안정적으로 유지한다. `MessageItem`의 `memo`가 전송 상태 변경 때문에 무효화되지 않도록 하기 위해서다.

## 8. 한계와 다음 단계

- **중복을 완전히 막지는 못한다.** 저장 확인 조회와 재전송 사이에 원래 요청이 서버에서 저장되면 중복된다. 유니크 제약이 있어야 이 틈이 닫히며, `client_id` 기반 멱등성을 다음 단계로 남긴다.
- **첫 메시지(채팅방 생성과 함께 전송)는 저장 확인을 건너뛴다.** 확인할 `chatId`가 아직 없다. 재전송 시 기존 채팅방을 재사용하지만 메시지 중복 가능성은 남는다.
- **같은 내용의 메시지를 동시에 여러 건 보내 모두 전송 중이면** 저장 확인이 서로의 결과를 가져갈 수 있다.
- **실패 상태는 메모리에만 있다.** 채팅방을 벗어나거나 새로고침하면 사라진다.
- **10초 기준은 일반 UX 기준이다.** 현지 네트워크 환경에 맞춘 조정은 하지 않았다.

## 9. 검증 방법

브라우저 개발자 도구에서 직접 확인한다.

1. **느린 네트워크:** Network를 Slow 3G로 두고 전송 → 1초 뒤 "전송 중..."이 표시되는지
2. **실패:** Network를 Offline으로 두고 전송 → 실패 표시와 재전송·삭제 버튼, 실패 메시지가 맨 아래에 고정되는지
3. **재전송:** Offline을 해제하고 재전송 → 버튼이 스피너로 바뀌고 성공 시 정상 말풍선이 되는지
4. **삭제:** 실패 메시지의 삭제 → 목록에서 제거되는지
5. **저장 확인:** 서버 응답만 지연시켜(Network 탭에서 응답 차단) 10초 뒤 서버에 저장된 메시지가 있을 때 실패가 아닌 성공으로 정정되는지
6. 1:1 채팅과 그룹 채팅 모두에서 위를 반복
