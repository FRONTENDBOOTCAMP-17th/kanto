## 1. [제안] 금칙어 검사를 서버 insert 경로에서도 강제하기

### 왜 필요한가

지금은 작성 폼(중고·렌탈·구인)이 브라우저에서 `check`를 호출해 막습니다.

```ts
// CreateUsedGoodsForm.tsx
const profanityRes = await fetch(`/api/admin/profanity-rules/check?text=...`).catch(() => null);
const profanityData = profanityRes ? await profanityRes.json().catch(() => null) : null;
if (profanityData?.blocked) {
  showErrorToast("부적절한 텍스트가 포함되었습니다");
  return;
}
```

문제는 두 가지입니다. 하나는 이 검사가 브라우저 코드라, 개발자 도구로 이 함수를 건너뛰거나 글 insert 요청을 직접 보내면 그냥 통과한다는 점이고, 다른 하나는 `.catch(() => null)`과 `check` 라우트 안의 `catch { blocked:false }` 때문에 규칙 조회가 한 번 실패하면 금칙어가 있어도 통과한다는 점(fail-open)입니다. 클라이언트 검사는 사용자에게 빠르게 알려 주는 UX 장치일 뿐이고, "이 글은 못 올라가야 한다"는 보장은 서버가 쥐고 있어야 합니다.

이미 같은 폼에서 도배 방지는 서버 라우트(`/api/posts/rate-check`)로 강제하고 있으니, 금칙어도 같은 결로 맞추면 됩니다.

### 어떻게

이미 `getProfanityRules()`와 필터 로직이 `check` 라우트에 있으니, 그걸 작은 함수로 빼서 **글을 insert하는 서버 액션 맨 앞에서 한 번 더** 호출하면 됩니다.

**1) 공용 판정 함수로 추출** (`src/services/admin/adminContent.ts` 등에):

```ts
import { getProfanityRules } from "@/services/admin/adminContent";

export async function containsProfanity(
  text: string,
  scope: "post" = "post",
): Promise<boolean> {
  if (!text.trim()) return false;
  const rules = await getProfanityRules();
  const lower = text.toLowerCase();
  return rules
    .filter((r) => r.scopes.includes(scope))
    .some((r) => r.words.some((w) => lower.includes(w.toLowerCase())));
}
```

`check` 라우트도 이 함수를 쓰도록 바꿔 두면 로직이 한 군데로 모입니다.

**2) 글을 넣는 서버 액션 첫머리에서 검사** (예: 중고 글 작성 서버 액션):

```ts
"use server";

export async function createUsedGoods(input: CreateUsedGoodsInput) {
  const text = [input.title, input.content].join(" ");
  if (await containsProfanity(text)) {
    return { ok: false, error: "부적절한 표현이 포함되어 등록할 수 없습니다." };
  }
  // ... 기존 insert 로직
}
```

이렇게 하면 클라이언트 검사는 그대로 두되(빠른 안내), 실제 차단은 서버가 맡게 됩니다. fail-open을 유지할지(규칙 조회 실패 시 통과) fail-closed로 갈지는 팀에서 정하시면 되는데, 금칙어는 "조회 실패 시 일단 통과"가 서비스 관점에서 크게 위험하진 않으니 지금처럼 fail-open으로 둬도 괜찮습니다. 다만 그 판단을 주석 한 줄로 남겨 두면 나중에 헷갈리지 않습니다.

> 참고: 글 insert가 서버 액션이 아니라 브라우저에서 직접 supabase insert를 하는 구조라면, 이 검사를 넣기 위해서라도 insert를 서버 액션으로 옮기는 게 맞습니다. 도배 방지를 서버로 옮긴 것과 같은 이유입니다.

## 2. [사소] 금칙어 규칙 목록 GET에 인증 걸기

`src/app/api/admin/profanity-rules/route.ts`의 `GET`은 지금 인증 없이 전체 규칙을 돌려줍니다.

```ts
export async function GET() {
  try {
    const data = await getProfanityRules();       // 누구나 금칙어 사전을 받아 볼 수 있음
    return NextResponse.json(data);
  } catch (e) { ... }
}
```

같은 파일의 `POST`가 이미 `getAdminUser()`로 막고 있으니, 그 한 줄을 GET에도 그대로 붙이면 됩니다.

```ts
export async function GET() {
  const admin = await getAdminUser();
  if (!admin) return NextResponse.json({ error: "권한이 없습니다." }, { status: 403 });
  try {
    const data = await getProfanityRules();
    return NextResponse.json(data);
  } catch (e) {
    return NextResponse.json({ error: (e as Error).message }, { status: 500 });
  }
}
```

주의: 이 목록은 관리자 화면에서만 부르고, 앞의 `check` 엔드포인트(일반 사용자용, boolean만 반환)와는 다른 라우트입니다. `check`는 그대로 열려 있어야 하니 건드리지 마세요.

## 3. [제안] 마이그레이션 재현성 한 번 확인

`20260706000000_public_profiles_and_lock_users.sql`이 anon PII 차단과 `public_profiles` 뷰를 잘 굳혔습니다. 여기에 한 가지만 확인해 두면 배포 스토리가 완성됩니다.

이 뷰는 `security_invoker=on`이라, anon이 조회할 때 anon의 users RLS 정책을 따릅니다. 그런데 users의 RLS enable 구문과 anon SELECT 정책(비삭제 행 공개)이 마이그레이션 파일에는 안 담겨 있습니다(테이블 원형이 Supabase 프로젝트 베이스라인에 있어서요). 그래서 완전 백지 상태에서 reset하면 뷰가 이름을 몇 개 돌려줄지 이 파일만으로는 장담이 어렵습니다.

확인 방법:

```bash
# 로컬 Supabase에서
supabase db reset          # 마이그레이션 전체 재적용

# anon 키로 두 가지만 확인
# (1) 이름이 나오는가 — 목록/채팅이 뜨려면 필요
curl "$URL/rest/v1/public_profiles?select=id,name&limit=3" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"

# (2) PII가 막히는가
curl "$URL/rest/v1/users?select=email,phone" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"    # []가 나와야 정상
```

만약 (1)에서 이름이 안 나온다면(뷰가 0행), users의 anon SELECT 정책도 마이그레이션에 함께 넣어 주면 됩니다. 예:

```sql
alter table public.users enable row level security;

create policy "anon 공개행 조회" on public.users
  for select to anon
  using (deleted_at is null);
```

급한 건 아닙니다. 지금 라이브는 안전하게 동작 중이고(실측 확인), 이건 "새 환경에 reset 한 방으로 세워진다"를 위한 마무리라, 취업 레포로 공개할 때를 대비한 정리로 보시면 됩니다.
