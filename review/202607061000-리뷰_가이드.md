## 1. [필수] 운영 DB의 보안 수정을 마이그레이션으로 굳히기

### 왜 이게 문제인가

지금 라이브 서비스는 안전합니다. anon 키로 `users`를 못 읽습니다. 그런데 그 상태를 만든 변경이 **운영 DB에만 손으로 적용됐고, 저장소의 마이그레이션에는 안 남아 있습니다.** 확인해보면 이렇습니다.

- `supabase/migrations/20260626000000_grant_anon_select_users.sql`은 지금도 `grant select on public.users to anon;`을 실행합니다. (RLS는 "행"을 거를 수는 있어도 "열"을 못 가리기 때문에, 여기에 permissive 정책이 하나라도 있으면 email·phone 같은 컬럼까지 통째로 열립니다. 이게 원래 구멍의 정체였습니다.)
- 서비스 전반이 쓰는 `public_profiles` 뷰의 **정의(`create view …`)가 어느 마이그레이션에도 없습니다.** `grep -rn public_profiles supabase/migrations/`로 확인해보면 결과가 없습니다.

그래서 지금 저장소를 그대로 새 환경에 `supabase db reset` 하면 두 가지가 동시에 터집니다. 먼저 `public_profiles` 뷰가 없어서 목록·상세·채팅·GO 쿼리(`rental.ts`, `chat.ts`, `go.ts`, `block.ts` 등이 전부 이 뷰를 참조합니다)가 죽고, 여기에 더해 anon `users` 노출 구멍이 그대로 되살아납니다. 지금 라이브 DB의 안전한 상태와 저장소의 마이그레이션 상태가 어긋나 있는 셈입니다.

### 어떻게 굳히나

새 마이그레이션 파일 하나를 추가해서 (1) `public_profiles` 뷰를 정의하고 (2) anon이 `users` 원본을 못 읽게 막으면 됩니다. 아래는 예시입니다. **실제 운영 DB에 지금 걸려 있는 뷰 정의·정책과 맞는지 대조한 뒤** 적용하세요(운영과 다르면 운영 쪽을 기준으로 맞춥니다).

```sql
-- supabase/migrations/20260706000000_public_profiles_and_lock_users.sql
-- 목적: 라이브 DB에 손으로 적용된 "anon users 차단 + public_profiles 뷰"를
--       마이그레이션으로 재현 가능하게 굳힌다. (새 환경 db reset 시에도 안전하게)

-- 1) 공개용 뷰: 안전한 컬럼만 노출한다.
--    security_invoker=on 이면 뷰를 조회하는 사용자의 권한으로 평가되어,
--    뷰가 원본 테이블 권한을 우회하는 사고를 막는다.
create or replace view public.public_profiles
with (security_invoker = on) as
  select id, name, avatar_url, auth_id, created_at, deleted_at
  from public.users;

grant select on public.public_profiles to anon, authenticated;

-- 2) 원본 users 는 anon 이 통째로 못 읽게 되돌린다.
--    (26일 grant_anon_select_users 로 열어둔 것을 닫는다.)
revoke select on public.users from anon;
```

여기서 한 가지 주의할 점이 있습니다. `security_invoker = on`으로 두면 뷰를 조회할 때 **조회자 권한으로** 원본 `users`를 읽으려 하기 때문에, 방금 anon의 `users` SELECT를 revoke하면 anon이 뷰조차 못 읽게 될 수 있습니다. 그래서 뷰가 anon에게도 열려야 한다면 두 가지 중 하나를 고릅니다.

- 뷰를 `security_invoker`로 두는 대신 **`users`에 "anon은 공개 컬럼만"이라는 RLS 정책을 유지**하되, 노출 범위를 뷰가 아니라 컬럼 GRANT로 제한한다. (Postgres는 `grant select (id, name, avatar_url) on public.users to anon;`처럼 **컬럼 단위 GRANT**를 지원합니다. 이게 사실 가장 깔끔한 방법입니다.)
- 또는 뷰를 `security_definer`(기본값)로 두고, 뷰 소유자 권한으로 원본을 읽되 뷰가 안전한 컬럼만 select하도록 둔다. 이 경우 anon에게는 `users` 자체 GRANT를 주지 않아도 됩니다.

지금 라이브가 실제로 어느 방식으로 막혀 있는지는 Supabase 대시보드의 SQL 에디터에서 아래로 확인할 수 있습니다.

```sql
-- anon 에게 걸린 users 권한 확인
select grantee, privilege_type, is_grantable
from information_schema.role_table_grants
where table_name = 'users' and grantee = 'anon';

-- public_profiles 정의 확인
select pg_get_viewdef('public.public_profiles'::regclass, true);
```

확인한 실제 상태를 그대로 마이그레이션에 옮겨 적으면, 저장소만 봐도 "왜 안전한지"가 재현됩니다. **적용 후에는 반드시 anon 키로 다시 한 번 실측**하세요.

```bash
# .env.local 의 URL·publishable 키로
curl -s -o /dev/null -w "%{http_code} " \
  "$URL/rest/v1/users?select=email,phone&limit=1" \
  -H "apikey: $KEY" -H "Authorization: Bearer $KEY"
# 200 이면서 [] 이거나 권한 오류면 정상. email/phone 이 내려오면 아직 열린 것.
```

## 2. [제안] CI lint를 게이트로 조이기 — 단, 발표 이후에

지금 `ci.yml`의 lint 스텝은 이렇게 돼 있습니다.

```yaml
- name: Lint
  run: npx eslint . --max-warnings=0
  continue-on-error: true
```

`continue-on-error: true`라서 lint가 실패해도 PR이 막히지 않습니다. 지금 error가 12개 남아 있으니, 이 줄을 지금 빼면 앞으로 모든 PR이 빨간불이 되어 발표 준비에 방해가 됩니다. 그래서 **남은 이틀은 이대로 두는 게 맞습니다.** 발표가 끝난 뒤, error를 0으로 정리하고 나서 이 한 줄을 지우면 그때부터 lint가 진짜 게이트가 됩니다. 그 사이엔 CI 로그에서 lint 결과를 눈으로 보는 용도로만 쓰면 됩니다.

error를 줄일 때 가장 많은 `react-hooks/set-state-in-effect`는 대개 이런 모양입니다.

```tsx
// MeetupListPanel.tsx
useEffect(() => {
  setQuery("");
  setMineTab("hosted");
}, [mode]);
```

`mode`가 바뀔 때 상태를 초기화하려는 의도인데, effect 안에서 곧장 `setState`를 하면 렌더가 한 번 더 돕니다. `mode`를 `key`로 올려 컴포넌트를 새로 마운트시키거나(`<MeetupListPanel key={mode} />`), 파생 상태라면 렌더 중 계산으로 옮기는 식으로 바꿀 수 있습니다. 급하지 않으니 발표 후 과제로 두세요.

## 3. [제안] 프로필 화면의 한국어 잔여 문구 i18n 처리

`/profile`을 영어로 열면 대부분 영문인데 "망고 지수", "지금 갱신", 그 아래 안내 문구가 한국어로 남아 있습니다. 다른 문구들처럼 메시지 키로 빼면 됩니다.

```tsx
// 지금 (하드코딩)
<h2>망고 지수</h2>

// 바꾼 뒤
const t = useTranslations("Profile");
<h2>{t("mangoScore")}</h2>
```

그리고 `messages/ko.json`·`messages/en.json`에 같은 키를 추가합니다. 데모를 영어로 진행할 계획이면 데모 동선 위 화면부터 우선 처리하고, 아니면 발표 후로 미뤄도 됩니다.

## 4. 남은 이틀 실행 순서 (D-2)

루트의 `마무리-가이드.md`가 큰 원칙(기능 동결, 데모 경로 잠그기, 배포본 확인)을 다루니 함께 보시고, 우리 조에 특정한 순서만 짧게 정리합니다.

1. **오늘(월): 배포본부터 맞춘다.** `npm run build`는 로컬에서 통과하는 걸 확인했습니다. 이제 배포 사이트에 오늘 변경이 올라갔는지, 배포 환경변수(Supabase URL·키, 결제 키, 사이트 URL)가 다 들어가 있는지 확인하세요. 로컬 `.env.local`에만 있고 배포엔 빠진 값이 있으면 그 기능이 배포본에서만 조용히 죽습니다.
2. **오늘~내일: 데모 경로를 배포본에서 손으로 걷는다.** 메인 → 목록(필터 개편) → 상세 → 로그인/회원가입(개편) → 채팅·결제 → 마이페이지 순서로, 하루 한 번은 처음부터 끝까지. 오늘 개편한 화면들이 전부 데모 동선 위에 있으니 여기서 멈칫하는 데가 없는지가 1순위입니다.
3. **공개/재배포 전: 1번(anon `users` 마이그레이션)을 반드시 처리.** 발표 자체엔 지장이 없지만, 이력서 레포로 공개되는 순간 재현 가능한 보안 항목이라 공개 전 마지막 관문으로 두세요.
4. **여유가 되면: 프로필 i18n·eslint error 정리.** 둘 다 발표 후로 미뤄도 되는 항목입니다.

지금 데모를 막는 버그는 없고, 오래 끌던 보안 항목도 라이브에서는 닫혔습니다. 남은 이틀은 새로 만드는 시간이 아니라 이미 되는 걸 안 깨뜨리는 시간이라 생각하고, 배포본 확인과 데모 경로 점검에 힘을 쓰면 좋겠습니다. 화이팅입니다.
