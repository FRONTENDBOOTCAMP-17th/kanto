# Kanto 18차 리뷰 해결 가이드 (2026-07-04)

리뷰 본문에서 짚은 것 중 실제로 손을 대야 하는 부분을 순서대로 정리했습니다. 우선순위는 리뷰 본문의 "이 조가 취업 레포로 먼저 할 3가지" 순서를 따라갑니다.

## 1. anon `users` 테이블 PII 노출 닫기 (최우선)

### 왜 문제인가

Supabase는 anon(publishable) 키만 있어도 RLS(Row Level Security)가 켜져 있지 않은 테이블은 아무나 조회할 수 있습니다. 지금 `users` 테이블이 그 상태라, 브라우저 개발자도구에서 anon 키만 복사하면 누구나 아래처럼 호출해 전체 회원 정보를 볼 수 있습니다.

```bash
curl "https://<project>.supabase.co/rest/v1/users?select=id,email,role,phone" \
  -H "apikey: <anon-key>"
```

지금은 이게 로컬 리뷰 환경에서만 재현되지만, 레포가 공개되고 anon 키가 `.env.example`이나 프론트 번들에 그대로 노출되는 순간, 코드를 아는 사람이라면 누구나 같은 요청을 그대로 재현할 수 있습니다. 즉 지금 이 상태로 공개하면 "취약점이 코드에 다 적혀 있는" 셈이 됩니다.

다행히 `messages`·`chats`·`transactions` 테이블은 anon으로 조회하면 0행이 나오는 걸 확인했으니, 프로젝트 전체 RLS 설정이 잘못된 게 아니라 `users` 테이블 하나만 정책이 비어 있거나 anon SELECT를 허용하는 정책이 걸려 있는 상태로 보입니다.

### 어떻게 고치는가

이미 `src/services/usedGoods/usedGoods.ts:102`처럼 공개 화면에서는 `public_profiles` 뷰(`id`, `name`, `avatar_url` 등 공개해도 되는 컬럼만)를 쓰고 있으니, 방향 자체는 맞게 잡혀 있습니다. 남은 일은 원본 `users` 테이블에 대한 anon 접근만 막는 것입니다.

Supabase 대시보드의 SQL Editor(또는 마이그레이션 파일)에서 아래 순서로 적용합니다.

```sql
-- 1) RLS가 꺼져 있다면 켠다
alter table public.users enable row level security;

-- 2) anon 역할에 SELECT를 허용하는 정책이 있다면 제거한다
--    (정책 이름은 대시보드 Authentication > Policies에서 실제 이름을 확인해서 넣는다)
drop policy if exists "Enable read access for all users" on public.users;
drop policy if exists "anon_select_users" on public.users;

-- 3) 로그인한 본인만 자기 행을 읽을 수 있게 허용한다
create policy "users_select_own_row"
  on public.users
  for select
  to authenticated
  using (auth.uid() = auth_id);

-- 4) 관리자는 전체를 읽어야 하는 화면이 있으므로, 서버 액션에서
--    service role(secret) 키로 접근하는 supabaseAdmin 클라이언트를 계속 쓰면 된다.
--    (requireAdmin()이 이미 걸려 있는 admin 서버 액션들은 anon 정책과 무관하게 동작하므로 영향 없음)
```

적용 후에는 반드시 다시 anon 키로 같은 요청을 날려서 빈 배열(`[]`)이 나오는지 확인하고, 동시에 마이페이지·프로필처럼 로그인한 사용자가 자기 정보를 보는 화면이 여전히 정상 동작하는지도 함께 확인해주세요. 정책을 너무 좁게 걸면 본인 정보 조회 화면이 깨질 수 있습니다.

공개 목록/상세 화면에서 다른 회원의 이름·아바타가 필요한 곳(중고거래 판매자 표시 등)은 지금처럼 `public_profiles` 뷰를 계속 쓰면 되고, 혹시 아직 원본 `users` 테이블을 직접 select하는 화면이 남아있다면 그 부분도 `public_profiles`로 옮겨주는 게 안전합니다.

## 2. CI에 lint 게이트 추가하기

### 왜 필요한가

지금 `.github/workflows/ci.yml`은 `tsc --noEmit`과 `npm run build`만 돌리고 있어서, 타입 에러나 빌드 실패는 막아주지만 `eslint`가 잡아내는 문제(예: `react-hooks/purity`, `no-explicit-any`)는 그냥 통과됩니다. 그래서 지금 eslint error가 14건이나 쌓여 있는데도 계속 머지가 되고 있는 겁니다. 지금 당장 14건을 다 고치긴 빠듯하더라도, CI에 lint 스텝만 넣어두면 앞으로 새로 들어오는 코드에서는 같은 문제가 줄어듭니다.

### 어떻게 고치는가

`npm run lint` 자체는 이미 `package.json`에 정의돼 있으니(`"lint": "eslint"`), workflow 파일에 스텝 하나만 추가하면 됩니다.

```yaml
# .github/workflows/ci.yml
jobs:
  typecheck-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm install
      - run: npx tsc --noEmit
      - run: npm run lint   # 여기 추가
      - run: npm run build
        env:
          # ... 기존 env 그대로
```

지금 14 error가 남은 상태에서 바로 넣으면 CI가 계속 빨간불이 될 텐데, 마감이 코앞이라 당장 전부 고치기 부담스럽다면 처음에는 `continue-on-error: true`를 걸어서 "실패해도 막지는 않지만 결과는 눈에 보이게" 해두는 것도 방법입니다.

```yaml
      - run: npm run lint
        continue-on-error: true   # 일단 경고만, 나중에 error 다 잡으면 이 줄 제거
```

시간이 되면 `react-hooks/purity` 계열(`PaymentCard.tsx:37` 등)부터 하나씩 잡아나가면서 이 줄을 지우는 걸 목표로 삼으면 좋겠습니다.

## 3. PaymentCard.tsx의 `Date.now()` 렌더 중 호출 고치기

### 왜 문제인가

`src/components/common/chat/chatPanel/room/PaymentCard.tsx:37`은 지금 이렇게 돼 있습니다.

```ts
Date.now() - new Date(transaction.created_at).getTime() > 24 * 60 * 60 * 1000;
```

렌더 함수(또는 렌더 중 계산되는 값)는 같은 props/state로 여러 번 실행되더라도 항상 같은 결과가 나와야 하는데, `Date.now()`는 호출될 때마다 값이 달라지기 때문에 리렌더 타이밍에 따라 "만료됐다/안 됐다"가 미묘하게 오락가락할 수 있습니다. React 19의 컴파일러나 Strict Mode에서 렌더를 두 번 실행해보는 경우 이 차이가 실제로 드러날 수 있고, eslint의 `react-hooks/purity` 규칙이 정확히 이 패턴을 잡아내는 겁니다.

### 어떻게 고치는가

만료 여부 계산을 `useMemo`로 감싸서, 의존성이 바뀔 때만 다시 계산하도록 바꿉니다.

```tsx
import { useMemo } from "react";

function PaymentCard({ transaction }: PaymentCardProps) {
  const isExpired = useMemo(() => {
    return (
      Date.now() - new Date(transaction.created_at).getTime() >
      24 * 60 * 60 * 1000
    );
  }, [transaction.created_at]);

  // ... isExpired를 그대로 사용
}
```

다만 이렇게 해도 컴포넌트가 리마운트되기 전까지는 "지금 이 순간" 만료 여부가 갱신되지 않는다는 한계가 있습니다. 결제 만료처럼 실시간으로 카운트다운을 보여줘야 하는 화면이라면, `useEffect` 안에서 `setInterval`로 주기적으로 상태를 갱신하는 방식을 함께 쓰는 것도 고려해볼 만합니다.

```tsx
const [now, setNow] = useState(() => Date.now());

useEffect(() => {
  const id = setInterval(() => setNow(Date.now()), 1000);
  return () => clearInterval(id);
}, []);

const isExpired = now - new Date(transaction.created_at).getTime() > 24 * 60 * 60 * 1000;
```

이렇게 하면 `Date.now()` 호출 자체는 `useEffect` 안(렌더 바깥)에서만 일어나고, 렌더 함수는 `now`라는 state 값만 참조하니 순수성 문제가 사라집니다. 결제 만료 안내처럼 사용자가 지켜보는 화면이라면 이 방식이 더 자연스러울 수 있습니다.
