## 1. 지난 리뷰(19차) 반영 현황

### [필수] 운영DB 보안수정이 마이그레이션 미반영 → 해결

19차에서 유일하게 남겼던 [필수]입니다. 라이브 DB에는 손으로 anon PII 차단과 `public_profiles` 뷰가 걸려 있는데, `supabase/migrations`에는 그게 없고 오히려 `20260626000000_grant_anon_select_users.sql`이 `grant select on public.users to anon`으로 통짜 SELECT를 열어 둔 상태였습니다. 이대로면 새 환경에 마이그레이션을 처음부터 적용했을 때 (1) 뷰가 없어 목록·채팅·GO가 깨지고 (2) anon PII 노출이 되살아나는 위험이 있었죠.

이번에 세 개의 마이그레이션이 들어오면서 정확히 그 구멍을 메웠습니다. 파일을 열어 확인했습니다.

- `20260706000000_public_profiles_and_lock_users.sql` (임태형, #578 "19차 코드 리뷰 반영"): `public_profiles` 뷰를 `security_invoker=on`으로 정의하고 `id, name, avatar_url, auth_id, created_at, deleted_at`만 노출, 그다음 `revoke select on public.users from anon`으로 26일에 열어 둔 통짜 GRANT를 회수하고, 공개해도 되는 6개 컬럼만 **컬럼 단위 GRANT**로 다시 허용했습니다. email·phone·role은 anon GRANT 대상에서 빠져 있으니 컬럼 권한 자체로 PII가 막힙니다. 이 접근이 좋은 이유는, RLS(행 필터)가 있든 없든 컬럼 GRANT만으로 민감 컬럼이 원천 차단된다는 점입니다. 방어선이 하나 더 생긴 셈이죠.
- `20260706120000_drop_unused_tables.sql` / `20260706130000_fix_stale_refs_and_dedupe_triggers.sql` (김도혁): 안 쓰는 테이블 정리에 더해, 삭제된 테이블(comments 등)을 참조하던 `cleanup_deleted_users()`·`get_active_users_count()` 함수를 고치고 중복 트리거를 정리했습니다. 이건 안 고쳤으면 배포 후에 조용히 터졌을 부분이라 잡아 둔 게 의미가 큽니다. 삭제 대기 유저가 있는 상태에서 크론이 돌면 옛 함수가 없는 테이블을 조회하다 통째로 롤백되고, 대시보드 "활성 사용자 수"도 마찬가지였을 겁니다.

라이브 실측으로도 안전을 확인했습니다. anon 키로:

- `GET /rest/v1/users?select=*&Prefer:count=exact` → 200, `content-range: */0` (0행)
- `GET /rest/v1/users?select=email,phone,role` → `[]`
- `GET /rest/v1/users?select=email,role&role=in.(admin,super_admin)` → `[]`
- `GET /rest/v1/public_profiles?select=id,name,avatar_url` → 200, id/name/avatar만 정상 반환

즉 마이그레이션으로도 굳혔고, 라이브에서도 PII가 안 내려옵니다. 7회 연속 이월하던 항목을 19차에 라이브에서 닫고, 이번에 마이그레이션으로까지 마무리한 흐름이라 좋게 봤습니다.

- **[제안]** 재현성 한 가지만 확인하고 가면 좋겠습니다. `public_profiles` 뷰가 `security_invoker=on`이라, 조회는 anon 권한 + anon의 users RLS로 평가됩니다. 그런데 users의 RLS enable 구문과 anon SELECT 정책(비삭제 행 공개)은 이 마이그레이션들 안에 없습니다(테이블 원형·정책이 Supabase 프로젝트 베이스라인에 있고 incremental 마이그레이션에는 안 담겨 있죠). 그래서 "완전 백지 상태에서 `supabase db reset`" 시 뷰가 행을 몇 개 돌려줄지는 이 파일들만으로는 보장되지 않습니다. 다만 이 마이그레이션이 실제로 닫는 위험 — 지금 라이브 DB에 다시 적용될 때 26일 GRANT가 되살아나는 것 — 은 정확히 처리됐으니 발표 전 급한 건 아닙니다. 시간이 나면 로컬에서 한 번 reset 후 anon으로 public_profiles가 이름을 돌려주는지, users가 PII를 막는지 눈으로 확인해 두면 배포 스토리가 완성됩니다.

## 3. 조원별

### 임태형(THLIMM)

이번 회차 가장 무게 있는 기여는 19차 [필수]를 직접 반영한 `#578`입니다. `public_profiles` 마이그레이션을 본인이 작성해 넣었고, 파일 헤더에 "라이브 뷰 정의·GRANT와 대조 후 적용하고 anon 키로 PII 안 내려오는지 실측하라"는 검증 주의까지 적어 둔 게 특히 좋았습니다. 보안 수정을 남기고 갈 때 "이건 라이브랑 대조가 필요하다"고 명시해 두는 습관은 실무에서 사고를 막는 태도라 그대로 이어가시면 됩니다. 그 외 GO 공유 URL 진입 시 참여 버튼 '처리 중...' 멈춤(`a5c0657`), 모바일 헤더 spacer가 flex-shrink되어 컨텐츠를 덮던 문제, 커서 포인터 전역 적용까지 자잘한 UX 결함을 정리했습니다.

### 김도혁(DoHyuk-Centric)

DB 정리 축을 맡았습니다. 안 쓰는 테이블 드롭과 함께, 삭제된 테이블을 참조하던 함수(`cleanup_deleted_users`, `get_active_users_count`)를 고치고 중복 트리거를 정리한 게 핵심입니다. 위에서도 적었지만 이건 "지금 화면엔 안 보이지만 배포 후 특정 조건에서 조용히 터지는" 부류라, 발표 전에 걸러 낸 값어치가 큽니다. 회원가입 약관 선로딩 후 메인 이동(`acb0256`)도 흐름이 매끄러워졌고요. 남은 건 없습니다.

### 이동근(dongkeun99)

관리자 화면 정합성을 여러 곳 손봤습니다. 특히 신고 내역·유저 상세에서 탈퇴 회원·삭제 게시글을 숨긴 수정(`5e4e357`, `4ebcf0b`)은 관리자가 이미 없는 데이터를 클릭하다 깨지는 상황을 막아 주는 실용적인 변경입니다. 감사 로그 드롭다운 UI 통일, KPI 카드 숫자 오버플로우, 운영 하위 페이지 모바일 레이아웃, 채팅 기록 말줄임까지 마감 직전 다듬기로 적절했습니다. 별도 [필수]는 없습니다.

### 박소유(soyu, 팀장)

이번 delta 절반가량을 맡았습니다. 금칙어 게시글 등록 차단(`0933c5f`), ESLint/CI 게이트(`5f01da6`), 회원가입 후 로그인 라우트, 공지 UI 버그, README 기여도 문서화까지 폭이 넓습니다. CI에 eslint를 물리고 error를 0으로 만든 건 앞서 칭찬한 그대로입니다.

금칙어 기능은 설계 자체는 깔끔합니다. `check` 엔드포인트가 `{blocked: boolean}`만 돌려주고 데이터를 일절 흘리지 않는 점, 관리자 CRUD(POST/PUT/DELETE)는 `getAdminUser()`로 role까지 확인하는 점은 잘 잡혀 있습니다. 다만 한 가지 결이 걸립니다.

- **[제안]** 금칙어 검사가 클라이언트에서만 강제되고, 게시글을 실제로 insert하는 서버 경로에는 재검사가 없습니다. 세 개의 작성 폼(중고·렌탈·구인)이 브라우저에서 `check`를 호출해 `blocked`면 제출을 막지만, 정작 글을 넣는 서버 액션/insert에는 금칙어 가드가 없어서, 자바스크립트를 끄거나 insert를 직접 호출하면 필터를 통째로 우회할 수 있습니다. 게다가 호출부가 `.catch(() => null)`이고 `check` 라우트 자체도 `catch { blocked:false }`라, 규칙 조회가 한 번 실패하면 그냥 통과합니다(fail-open). 흥미로운 건, 같은 작성 폼에서 도배 방지(`rate-check`)는 이미 서버 라우트로 강제하고 있다는 점입니다 — 그 패턴을 금칙어에도 그대로 적용하면 됩니다. "막아야 하는 검증은 서버에서 한 번 더, 클라이언트 검사는 UX용"이라는 원칙으로 보면 자연스럽게 채워지는 자리라 [제안]으로 둡니다. 해결 방법은 가이드에 단계로 적어 뒀습니다.
- **[사소]** `GET /api/admin/profanity-rules`(규칙 목록)에는 인증이 없어서 누구나 금칙어 사전을 통째로 받아 볼 수 있습니다. 민감 데이터는 아니지만, 필터를 우회하려는 사람에게 정답지를 주는 셈이라 여기도 `getAdminUser()`를 한 줄 걸어 두면 깔끔합니다(변이 라우트엔 이미 걸려 있습니다).

## 4. 팀 공통
