## 1. [필수·보안] anon 키로 `users` 테이블이 통째로 읽히는 문제 닫기

### 지금 무슨 일이 벌어지나
브라우저에 내려가는 공개 키(publishable)만으로 이게 됩니다.

```bash
curl "https://<프로젝트>.supabase.co/rest/v1/users?select=email,role,phone&role=eq.admin" \
  -H "apikey: sb_publishable_..." -H "Authorization: Bearer sb_publishable_..."
# → 관리자 이메일 + 실제 휴대폰 번호가 그대로 응답됨
```

원인은 `users` 테이블에 anon(익명)의 SELECT를 허용하는 RLS 정책이 남아 있거나 RLS 자체가 꺼져 있기 때문입니다.

### 고치는 순서

**(1) 지금 상태 확인** — Supabase 대시보드 → SQL Editor:

```sql
-- RLS 켜져 있는지
select relname, relrowsecurity from pg_class where relname = 'users';
-- 어떤 정책이 걸려 있는지
select policyname, roles, cmd, qual from pg_policies where tablename = 'users';
```

`relrowsecurity`가 false거나, `roles`에 `anon`/`public`이 있고 `qual`이 `true`인 SELECT 정책이 보이면 그게 구멍입니다.

**(2) RLS 켜고, anon 전체 열람 정책 제거**

```sql
alter table public.users enable row level security;

-- anon/public에게 전체를 열어주던 정책이 있으면 삭제 (이름은 위 조회 결과로 바꾸세요)
drop policy if exists "Enable read access for all users" on public.users;
drop policy if exists "users_select_all" on public.users;
```

**(3) 꼭 필요한 접근만 다시 허용** — 로그인한 본인이 자기 행만 보게:

```sql
create policy "users can read own row"
on public.users for select
to authenticated
using ( auth_id = auth.uid() );
```

**(4) 목록/카드에 필요한 공개 정보(이름·아바타)는 이미 만들어 둔 `public_profiles`로** — 지금 `usedGoods`·`go`·`block` 등에서 `users:public_profiles!...`로 옮기고 있는 그 방향이 정답입니다. 남은 조인들도 원본 `users`가 아니라 `public_profiles`(id·name·avatar만)를 보게 마저 옮기면, 이메일·전화번호가 애초에 조회 대상에서 빠집니다.

**(5) 검증** — (1)의 curl을 다시 날려서 **빈 배열 `[]` 또는 401/403**이 나오면 닫힌 겁니다. 로그인 상태에선 본인 프로필이 정상적으로 보이는지도 함께 확인하세요.

> 참고: 서버(서버 컴포넌트·서버 액션·API 라우트)에서 관리자 화면용으로 `users`를 읽을 땐 `createAdminClient()`(service_role)를 쓰고 있으니, RLS를 켜도 관리자 화면은 그대로 동작합니다. 막히는 건 오직 브라우저에서 직접 때리는 anon 경로입니다.

## 2. [제안] 번역 API가 죽어도 공지는 저장되게

`lib/translate.ts`에서 실패 시 원문으로 폴백:

```ts
export async function translateNoticeTitle(title: string) {
  try {
    const res = await fetch(/* mymemory ... */);
    if (!res.ok) throw new Error(`translate ${res.status}`);
    const json = await res.json();
    const translated = json?.responseData?.translatedText;
    if (!translated) throw new Error("empty translation");
    return translated;
  } catch {
    return title; // 번역 실패 = 원문 그대로. 공지 저장은 막지 않는다.
  }
}
```

이렇게 하면 외부 API가 rate limit에 걸리거나 다운되더라도 공지는 원문 제목으로 정상 저장되고, 화면 표시단의 `?? title` 폴백과도 자연스럽게 맞물립니다.

## 3. [제안] 도배 방지를 서버에서 강제하기

지금은 이런 모양입니다(클라이언트):

```ts
// useCreateJobForm.ts (요지)
const { data } = await fetch("/api/posts/rate-check");   // 검사
if (data.exceeded) return alert("잠시 후 다시");
await supabase.from("posts").insert({ ... });            // 강제 없는 삽입
```

검사와 삽입이 따로 놀기 때문에 삽입만 반복 호출하면 검사를 통째로 건너뛸 수 있습니다. 삽입을 서버 액션 안으로 옮기고, 그 안에서 카운트를 확인하도록 바꿔주세요.

```ts
// app/(user)/.../actions.ts
"use server";
export async function createJobPost(input: JobInput) {
  const userId = await requireUser();            // 인증
  // 최근 N분 내 이 사용자의 작성 수 확인
  const since = new Date(Date.now() - 10 * 60 * 1000).toISOString();
  const { count } = await admin.from("posts")
    .select("id", { count: "exact", head: true })
    .eq("user_id", userId).gte("created_at", since);
  if ((count ?? 0) >= LIMIT) throw new Error("RATE_LIMIT");
  await admin.from("posts").insert({ ...input, user_id: userId });
}
```

클라이언트는 이 액션을 호출만 하면 됩니다. 검사와 삽입이 한 몸이라 우회가 안 됩니다. (더 튼튼하게는 DB 트리거로 시간당 삽입 수를 제한할 수도 있지만, 지금 단계에선 서버 액션 이관으로 충분합니다.)

## 4. [사소] 감사 로그 await + CI eslint

- `insertAuditLog(...)` 앞에 `await`를 붙이세요. serverless는 응답 반환 뒤 바로 종료돼서 await 없는 insert가 유실됩니다.
- CI(`.github/workflows/ci.yml`)에 eslint 단계 추가(당장 error를 다 못 고치면 `continue-on-error`로라도):

```yaml
      - name: Lint
        run: npx eslint . --max-warnings=0
        continue-on-error: true
```
