## 2. 이번 [필수] — 보안 (실측)

### [필수·보안] anon 키로 `users` 테이블 전체가 읽힙니다 (관리자 이메일·전화번호 노출) — 팀 공통, 최우선

이건 12차부터 반복해서 짚고 있는데 이번에도 그대로 열려 있고, 오히려 노출 범위가 넓어졌습니다. 브라우저에 심어지는 publishable 키(`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`)만으로 아래가 그대로 나옵니다.

```
GET /rest/v1/users?select=email,role,phone → HTTP 206, 124행
GET /rest/v1/users?role=in.(admin,super_admin) →
  soyupark1997@gmail.com (super_admin, phone 09216410567)
  ehgur8527@naver.com    (super_admin, phone 01094006992)
  dglee6896@gmail.com    (super_admin, phone 01044444444)
  admin@kanto.com / asdf1234@naver.com / mark6896@naver.com (admin) ...
```

publishable 키는 브라우저에 내려가는 **공개 키**라서, 이건 사실상 "누구나 우리 회원 124명의 이메일과, 관리자 몇 명의 실제 휴대폰 번호를 조회할 수 있다"는 뜻입니다. `role=eq.admin` 필터 한 줄이면 관리자만 골라낼 수 있어서, 계정 탈취를 노리는 입장에선 표적 목록을 그냥 받아가는 셈이라 심각합니다.

다행히 `messages`·`chats`·`transactions`는 RLS가 걸려 anon으로 0행이었고(잘 되어 있습니다), 문제는 오직 `users` 테이블입니다. 조인용으로 만든 `public_profiles`(id·name·avatar만) 뷰로 이미 곳곳을 옮기고 있는 방향(칭찬)인데, 정작 원본 `users` 테이블의 anon SELECT를 아직 안 막았습니다. 처방은 가이드 문서 1번에 SQL로 정리했습니다. **이번 주 안에 이거 하나만큼은 꼭 닫읍시다.**

## 3. 이번 delta — 조원별 리뷰

어제 올라온 새 코드는 전반적으로 품질이 좋습니다. `tsc --noEmit` 통과했고, 차단·인가 검증이 클라이언트와 서버 양쪽에 이중으로 걸려 있어서 지난 리뷰들에서 강조했던 패턴이 이제 자연스럽게 몸에 배어가고 있음이 느껴집니다.

### 이동근(@dongkeun99) — 차단 채팅 방지 / 삭제·판매완료 오버레이 / 정지 표시

- **[칭찬] 차단 서버 검증 이중화** — `chat/room/actions.ts`의 `sendMessageAction`·`createChatAndSendAction` 양쪽에 `isBlockedPair` 검사가 들어가 있습니다. UI에서 입력창을 disable하는 데서 그치지 않고 서버에서 한 번 더 막고, 실패 시 낙관적 메시지를 롤백하는 것까지 정석대로입니다. 차단은 "UI만 막으면 우회된다"의 대표 사례라 서버에서 잡은 게 정확합니다.
- **[사소] 채팅 입력 핸들러의 클라이언트 가드** — `ChatRoomClient.tsx`에서 차단 상태(`getBlockStateAction`)가 async로 로드되는 아주 짧은 순간엔 이론상 전송 시도가 가능하지만, 위처럼 서버가 최종적으로 막아주므로 실제 우회는 안 됩니다. 굳이 다듬는다면 `handleSend` 첫 줄에 `if (isBlocked) return;` 한 줄이면 됩니다. 필수 아닙니다.
- **[사소] "정지 해제 시 망고 지수 복원"** — 실제로는 정지 중일 때 점수 바 대신 안내를 보여주고, 저장된 점수는 그대로 두는 방식이라 동작은 맞습니다. 다만 커밋 메시지가 "복원"이라고 되어 있어 로직보다 커지게 표현됐습니다. 만약 정지 중에 점수를 실제로 깎았다가 되돌리는 의도였다면 그 감산/복원 지점이 따로 있어야 하니 한 번 확인해 주세요.

### 임태형(@THLIMM) — 구인구직/계좌등록/회원가입/관심카테고리 핫픽스

- **[제안] 도배 방지가 클라이언트 사전 확인만 있고 서버 강제가 없습니다** — `useCreateJobForm.ts`·`useCreateUsedGoodsForm.ts`가 글쓰기 전에 `GET /api/posts/rate-check`로 최근 작성 수를 확인하는데, 정작 실제 insert는 브라우저 Supabase 클라이언트로 `posts` 테이블에 직접 넣습니다. rate-check 라우트 자체는 auth·시간창·카운트 로직이 잘 짜여 있지만, 검사를 클라이언트 쪽에서 "권유" 형식으로 두면 rate-check를 건너뛰고 insert만 반복했을 때 도배가 그대로 통과됩니다. 검사와 강제가 같은 지점(서버)에 있어야 의미가 생깁니다. 처방은 가이드 3번에 정리했습니다.

### 박소유(@soyupark1997) — 공지 번역 / 인기 구인 / i18n

- **[제안] 번역 API 실패가 공지 등록 전체를 막습니다** — `lib/translate.ts`의 `translateNoticeTitle`이 무료 외부 API(mymemory)를 `await`로 호출하고 200이 아니면 `throw`하는데, 이 예외가 `createNotice`/`updateNotice` 앞에서 터지면 번역이 안 됐다는 이유로 공지 작성 자체가 실패합니다. 무료 API는 rate limit·다운이 잦아서, 운영 중에 갑자기 공지를 못 올리는 상황이 생길 수 있습니다. 표시단엔 이미 `?? title` 폴백이 있으니, 저장 시에도 번역 실패하면 원문 title로 폴백하고 공지는 정상 저장하도록 `try/catch`로 감싸주면 됩니다(가이드 2번).
- **[사소] 감사 로그가 비-await(fire-and-forget)** — `api/admin/popular-jobs/route.ts`·`notices/route.ts`에서 `insertAuditLog(...)`를 `await` 없이 부릅니다. serverless는 응답을 반환하는 순간 함수가 종료되기 때문에 await 없는 insert는 유실될 수 있습니다. 권한 행동 추적 로그가 빠지면 나중에 감사할 방법이 없으니 `await`를 붙여주세요. (인가 검증 자체는 GET/PATCH 모두 super_admin 체크에 값 범위 검증까지 탄탄하게 잘 짜여 있습니다.)
